# 统一调试与日志系统设计

> 本文件只写机制、接口契约和验收口径；任务状态、优先级与任务编号只在 [00-当前状态与任务.md](00-当前状态与任务.md)。本设计落地后，再整体翻新 [04-构建与真机调试.md](04-构建与真机调试.md) 的真机调试部分。

## 目标

把现在分散的排查方式收敛成一套可重复使用的开发调试流程：

1. 一个统一 debug 启动命令。
2. 一份活跃统一日志，能同时看到 wiliwili、兼容层、播放器和音频的状态。
3. 在 debug/诊断运行时，每次内容加载都有权威内容标识和 session，覆盖视频、番剧、直播、动态/图文，不靠 cid/oid 反推。
4. 能用命令在真实 wiliwili 实例里复现页面跳转和播放器操作，不需要开发者手工点 UI。
5. `dmesg` 随 debug 命令自动采集，并用 run id / 时间戳与统一日志对齐。
6. 后续真机回归脚本只消费这套输出，不再自建第二套日志体系。

## 非目标

- 不在设计阶段改播放逻辑或重写回归脚本。
- 不把内核 `dmesg` 混进应用日志；它是旁证附件，通过时间线关联。
- 不恢复已封存的 `test-3.5c.sh` / `compat_test` 作为回归入口。
- 不在正式启动路径默认打开高频诊断。
- 不在设备 NAND 上保存常规历史日志；设备只保留当前活跃日志，归档在开发机本地。
- 第一版不做外部控制 socket；先做启动期 debug 控制器，必要时再加调试构建专用命令通道。

## 上游日志与调用面扫描结论

### 日志

- wiliwili 用 `brls::Logger` 输出 UI / presenter / 播放页日志；`main.cpp` 支持 `-d` 打开 debug 级、`-t` 打开 mpv terminal、`-o <file>` 另开日志文件。
- 统一方案不使用 `-o`，避免 wiliwili logger 与 daemon stderr 分裂成两份文件。
- 上游日志没有统一的播放 session / 内容类型字段，只是各模块零散 `brls::Logger::debug/info`；本分支需要在关键入口补结构化 session 行。

### 导航与页面

- `Intent::openBV/openAV/openSeasonBySeasonId/openSeasonByEpId/openLive/openActivity/openSearch/openSetting/openMain/...` 是上游现成的导航入口，内部通过 `brls::Application::pushActivity()` 打开对应 Activity。
- `main.cpp` 中注释掉的 `Intent::openBV`、`Intent::openLive`、`Intent::openSearch` 等是启动期调试入口，但只支持编译前注释/解注释，不能算自动化框架。
- 可通过 debug-only 控制器在 `brls::sync()` 中调用这些 `Intent`，无需伪造手柄或鼠标点击。

### 播放器功能

- `MPVCore` 提供 `setUrl`、`resume`、`pause`、`seek`、`seekRelative`、`seekPercent`、`setVolume`、`setSpeed`、`isPlaying` 等调用面。
- `VideoView` 通过 `APP_E` 接收 `HINT`、`QUALITY_CHANGE`、`LAST_TIME`、`SET_QUALITY` 等页面级动作。
- 播放器自动化应调用现有 `MPVCore` / `Intent` / 必要的 debug-only helper，不能绕开 UI 自建第二套播放链。

## 当前统一日志事实

- 当前主菜单入口是 `tools/steamlink-app/wiliwili.sh`，它清空并把 wiliwili stdout/stderr 追加到 `/tmp/wiliwili.log`。
- `mpv-stub` fork daemon 时未重定向 stdout/stderr，因此 `[mpv-compat]`、`[SlPlayer]`、`[SlAudio]`、`[SlHttp]`、`[vpu]` 实际已经继承同一个 fd，写进 `/tmp/wiliwili.log`。
- `/tmp/ui.log` 是旧 `tools/launch-wiliwili.txt` 直接启动方式的残留，不是当前主菜单路径。
- 当前 `SL_MEDIA_TAG` 是 `--open-bv` 在进程启动时设置的全局环境变量，切片后不会更新，不能当当前内容标识。
- 设备是 BusyBox 1.24.1 的 `dmesg`，`--help` 只支持 `-c/-n/-s/-r`，**不支持 `dmesg -w`**。

## 内容身份模型

公共字段：

```text
run=<run-id> session=<session-id> content=<type> id=<primary-id> bv=<bvid-or-empty>
```

| content | 权威主标识 | 附加字段 | 来源 |
|---|---|---|---|
| `video` | `bvid` | `cid`、`aid`、`qn`、宽度、高度、fps、start | `videoDetailResult.bvid`、`videoDetailPage.cid` |
| `season` | `ep_id` 或 `season_id` | `bvid`、`cid`、`aid`、`qn` | `episodeResult`、`seasonInfo` |
| `live` | `room_id` | `uid`、标题、清晰度 | `LiveActivity(roomid)`、`liveRoomPlayInfo` |
| `dynamic` | `dynamic_id` / `id_str` | 嵌套引用：`video.bvid`、`video.epid`、`live.room_id`、图片数量 | `Intent::openActivity(id)` → `DynamicArticleDetail(id)` → `requestDynamicArticle(id)` |
| `gallery` | 图片集合 id 或来源 dynamic id | 图片数量、来源 | `Intent::openGallery(data)` |
| `page` | 页面名 | 搜索词、收藏夹 id、设置项等 | `Intent::openSearch/openCollection/openSetting/...` |

约束：

- BV 只是 `video` / `season` 的主标识之一；直播用 room id，动态用 dynamic id。
- `bv` 对 `video` / `season` 必填，即使 `id` 已经是 BV 也重复记录一份，确保自动复测不需要反推；`live` / `dynamic` / `page` 可为空。
- cid/oid 只作辅助字段，禁止从 cid 反推 BV。
- 不写签名 URL、upsig、trid、buvid 等查询参数。
- debug 运行时每次 loadfile/open 生成新 session；同一场播放内的 seek/pause/audio 事件都带同一 session。正式启动路径默认不打开这套结构化日志。

## 接口契约

### ID 约定

- `run id`：由 debug.sh 在开发机生成，格式 `YYYYMMDD-HHMMSS-<pid>`，贯穿一次 debug 进程。
- `session id`：由 UI debug 控制器在内容加载前生成，格式 `<run-id>-<counter>`，同一 run 内单调递增。
- `request id`：沿用兼容层现有 `ctx->requestSeq`；命令日志和 IPC 事件都记录它。
- `generation`：沿用兼容层文件代次；watchdog 恢复后 generation 变化，但 session 不变。

### 日志行格式

```text
[HH:MM:SS.mmm][SOURCE][run=<id>][session=<id>] message
```

`SOURCE` 至少包含 `UI`、`COMPAT`、`PLAYER`、`AUDIO`、`HTTP`。实施初期解析器兼容现有 `[SlPlayer]` / `[SlAudio]` / `[mpv-compat]` / `brls::Logger` 前缀；输出层逐步统一。

必须提供的日志样例：

```text
[UI][run=...][session=...] content start content=video id=BV... bv=BV... detail=cid=... aid=... qn=...
[mpv-compat] loadfile: gen=... req=... tag=... url=... extra_keys=referrer,network-timeout,audio-file,run,session,content,id,bv
[daemon][life] ... run=... session=... bv=BV... open enter req=... opened=...
[SlPlayer][media] oid=... qn=... audio=... duration=... widthxheight fps=...
[CMD] seek run=... session=... req=... name=seek_forward target=120 status=start
[EVT] seeked run=... session=... gen=... req=... position=120.033 status=ok
[PLAYER] audio start run=... session=... target=... present=... skip=...
[UI] content end run=... session=... reason=eof|user_stop|error
```

### UI → compat → daemon 透传

1. UI debug 控制器生成 run/session，写入 `VideoView::genExtraUrlParam()` 产出的 extra：`run=<run-id>,session=<id>,content=<type>,id=<primary>,bv=<bvid-or-empty>`。
2. `mpv_stub.c` 的 `build_open_cmd()` 解析这些键，并在 `open` 帧前发送新增 `meta` 帧：`meta<TAB>gen<TAB>req<TAB>run=<run-id><TAB>session=<id><TAB>content=<type><TAB>id=<primary>[<TAB>bv=<bvid>]`。
3. daemon 按 generation 保存 meta；同 generation 的 `open/seek/pause/audio/progress/error` 日志都带 run/session 前缀，video/season 还带 bv 前缀。
4. watchdog 回放 open 时复用同 generation 的 meta；generation 变化时由 compat 重新发送 meta。
5. `SL_CMD_OPEN` 原有字段顺序不变，meta 是新命令，不把 session 塞进 URL 或 referrer。

### D22 健康提示事件契约（已实现）

D22 已扩展 heartbeat，并在 compat 侧复用 500ms 轮询；软卡顿事件不经过 daemon IPC，而是 compat 生成 mpv 属性事件供 wiliwili 消费：

```text
heartbeat<TAB>gen<TAB>req<TAB>lastFrameTimeMs<TAB>stage<TAB>playing<TAB>inTransition<TAB>videoFrames<TAB>currentPaused<TAB>targetPaused<TAB>seeking<TAB>workerAlive<TAB>presentationMs<TAB>videoQueueMs<TAB>networkErrorAgeMs
sl-health-stall = 1  (MPV_EVENT_PROPERTY_CHANGE, MPV_FORMAT_FLAG)
```

- `presentationMs` 用播放线程现有无锁 `position_`，`networkErrorAgeMs` 用新增原子时间戳；compat 不需要调用 `stats()`。
- compat 复用 500ms heartbeat 轮询，在软卡顿首次命中时发一次属性事件；每个 generation/session 只发一次，不新增高频轮询线程。
- compat 把它映射为播放页一次性提示，通过现有 `APP_E -> VideoView::HINT` 显示；事件不属于播放失败，不触发 watchdog、不关闭透明层、不生成 `END_FILE(ERROR)`。
- UI 收到后只显示“播放不流畅，可尝试切换到 720P”，不自动降清晰度、不重开播放、不写默认清晰度设置。
- 日志只记录状态转换：`health stall detected -> hint shown`，不输出每秒诊断。compat 行带 run/session/gen/req 和数值快照，UI 行带 run id。
- 调试参数：`SL_HEALTH_WINDOW_MS`（默认 8000）、`SL_HEALTH_PROGRESS_MS`（默认 250）、`SL_HEALTH_NET_GRACE_MS`（默认 3000）、`SL_HEALTH_FORCE=1`。`debug.sh` 对应参数为 `--health-window-ms`、`--health-progress-ms`、`--health-net-grace-ms`、`--health-force`，并写入 manifest。

debug.sh 通过 `/tmp/launch_cmdline.txt` 设置环境变量，不把调试参数传给 wiliwili 本体：

SL_DEBUG_CONTENT=video:BV1Nvx16TEzY:cid
SL_DEBUG_SCENE=seek_forward

参数形态：

```text
video:<bvid>[:<cid>]
season:ep:<ep_id> | season:<season_id>
live:<room_id>
dynamic:<dynamic_id>
page:<search|setting|collection|...>:<arg>
```

### 场景命令契约

| 场景 | 参数 | 触发方式 | 完成判据 |
|---|---|---|---|
| `play` | 无 | `Intent::open*()` | `PLAYBACK_RESTART` 且 `isPlaying()` |
| `seek_forward` / `seek_backward` | `target=<秒>` 或 `delta=<秒>` | `MPVCore::seek/seekRelative` | `SEEKED` 事件 req 匹配，且 progress 到达目标附近 |
| `pause_resume` | `after=<秒>` | 首帧后 `pause()`，再 `resume()` | 依次收到 `Paused`、`Resumed` |
| `quality_change` | `qn=<码>` | debug-only helper，直接设置质量并重新请求播放地址 | 新 session 的 `open` 完成 |
| `page_nav` | `target=<page>` | `Intent::open*()` | 目标 Activity 创建，返回主页面无 crash |
| `live_connect` | 无 | `Intent::openLive()` | 流 open、弹幕连接事件完成 |
| `dynamic_open` | `target=<dynamic_id>`、`nested=<video|live|ep>` | `Intent::openActivity()` + 嵌套跳转 | 动态详情加载，嵌套目标打开 |

每条命令写 `CMD ... status=start`，完成/失败写 `CMD ... status=ok|timeout|error`。默认完成超时沿用现有 30 秒等待；具体数值作为 `SL_DEBUG_TIMEOUT_MS` 可调，待真机校准。

### 日志清理与归档契约

- debug.sh 启动前拉取已有 `/tmp/wiliwili.log` 到 `debug-runs/<run>/prestart.log.gz`；拉取失败则中止启动，不清空设备日志。
- debug.sh 前台启动 wiliwili.sh 并等待其退出，不经过 shell 主菜单自动重启循环；正常主菜单启动流程不变。
- wiliwili.sh 继续负责清空 `/tmp/wiliwili.log` 和写 boot 行；boot 行增加 `run=<id>`（由 `SL_DEBUG_RUN_ID` 提供）。
- debug.sh 在 EXIT/INT/TERM trap 中拉取最终日志、dmesg 和 manifest 到本地。
- 调试归档放开发机 `debug-runs/<run>/`，不写设备 NAND，不入库、不 push。

### 敏感信息契约

以下日志点必须改为只输出脱敏标识：

- `wiliwili/source/view/mpv_core.cpp` 的 `url/extra` debug 输出。
- `tools/mpv-stub/mpv_stub.c` 的 `loadfile ... %s` 输出。
- `player/daemon/slplayer_daemon.cpp` 的 `open ... %s` 输出。

脱敏后只保留 `bvid/cid/oid/qn` 和静态路径片段；禁止输出 `?` 后查询串、`upsig`、`trid`、`buvid`。

## 统一日志

### 单一活跃文件

活跃日志固定为 `/tmp/wiliwili.log`，不使用 `-o`，不为播放器另建日志文件。设备只保留当前一次运行；历史全部拉回开发机本地 `debug-runs/<run-id>/`，该目录已在 `.gitignore` 中忽略。

### 关键事件时间线

统一日志需要能拼出以下时间线，每行带同一 session 和 request id：

1. `content session start`
2. `loadfile / open`
3. `seek enter / seek return`
4. `first frame submitted`
5. `queue stable`
6. `audio position reached / audio start`
7. `pause / resume`
8. `fatal / watchdog / error`
9. `health stall detected / hint shown`
10. `content session end`

直播没有 seek/pause 语义时，记录连接、弹幕连接、流切换和错误即可；动态/图文记录页面打开、嵌套内容跳转和返回。

## dmesg 关联

- 启动时保存 `dmesg.before.txt`，写统一日志 run id 和设备时间。
- 每个场景命令开始/结束保存一次 `dmesg.<scene>.<n>.txt`，避免持续轮询。
- 退出时保存 `dmesg.after.txt`；附件名都带 run id。
- 分析时按 run id + 时间戳对齐，不把 dmesg 文本混入应用日志。

## 设计意图确认记录（2026-11-19）

用户确认以下默认建议全部按方案执行：

1. **构建边界**：D27 的 debug 控制器、`meta` IPC 和结构化 session 日志只进 dev 构建；正式包不携带测试入口。
2. **session 生命周期**：每次 loadfile/open 新建 session；清晰度切换新建 session；备用源切换和 watchdog 恢复复用原 session，只增加 generation。
3. **自然播放缺少 BV**：允许 `bvid=unknown`，以 cid/oid 和内容类型标明来源；禁止从 cid 反推 BV。
4. **动态嵌套跳转**：从动态卡片跳到视频/直播/番剧时新建独立 session，并记录 `parent_session=<dynamic-session>`。
5. **命令控制时机**：第一版只支持启动期场景，不支持运行中对已打开实例发命令。用户强调：以后用户通知“测试某场景”时，必须严格按统一 debug 启动流程触发；从主菜单启动、手动写 `launch_cmdline.txt` 或进入应用后再手工操作，都不算按该场景测试。启动流程是触发条件的一部分，见 [04](04-构建与真机调试.md) 和 [07](07-开发纪律.md)。
6. **quality_change**：接受新增 dev-only helper 直接切清晰度，但必须复用原生质量设置和 `updateVideoLink()` 路径，不打开质量下拉框。
7. **seek 完成判据**：同时检查 `SEEKED` 事件 req 匹配和 progress 到达目标附近；容差先用 250ms 或一帧量级，后续真机校准。
8. **dmesg 深度**：第一版用启动前、命令边界和结束多点快照；是否足够捕获 VPU/SHM 瞬时错误由真机验证后决定。
9. **脱敏强度**：彻底禁止 `?` 后查询串，只保留 `bvid/cid/oid/qn` 和静态路径片段。
10. **归档保留**：第一版不自动清理 `debug-runs/`，由人工管理；manifest 记录大小和创建时间，保留上限后续再加。

### 冲突分类

| 类型 | 判定 | 处理 |
|---|---|---|
| 文档事实错误 | 代码/SDK 已明确实现，且不改变本文意图 | 改文档，不改代码；在 [02](02-开发进度日志.md) 记录文件、行号和证据 |
| 实现偏离契约 | 代码行为与已拍板接口/验收不一致 | 默认改代码回到契约；若契约本身不可行，先停止并提请拍板 |
| 设计假设被真机推翻 | 日志、截图或用户确认与本文推断相反 | 以真机证据为准；暂停相关实现，更新设计后再继续 |
| 上游机制不兼容 | 实现需要大改 wiliwili 或破坏上游调用链 | 优先复用上游机制；确需偏离时写出 patch 边界并由用户拍板 |

### 拍板边界

- 实现者/Codex 可自行决定字段名细节、文件布局、内部函数名、日志文案和局部错误分支，前提是**不改变接口契约、行为边界和验收口径**。
- 用户拍板：内容身份模型、session 字段、IPC 命令格式、debug 启动参数、正式包与 debug 构建边界、默认行为、安全脱敏规则和验收标准。
- UI、画面、声音、同步结论必须由用户真机确认；AI 不能因为日志“看起来对”就改验收结论。

### 必须记录的冲突模板

每次冲突写入 [02](02-开发进度日志.md)：

```text
计划条款：<本文章节/条款>
真实情况：<文件、行号、日志或真机证据>
影响：<对接口/行为/验收的影响>
候选方案：<改代码 / 改计划 / 补实验>
最终决定与拍板人：<...>
```

### 停止条件

出现以下情况必须先停下来确认，不能做静默兼容：

- 需要改变 `meta` / `open` IPC 契约或 session 字段。
- 需要让正式包默认进入 debug 行为。
- 需要把签名 URL、trid、buvid 等敏感参数重新写进日志。
- 需要绕开 `Intent` / `MPVCore` 自建第二套播放或页面调用链。
- 真机用户结论与设计假设相反。

## 待校准项

这些不阻塞开工，但必须在落地中通过真机数据回填：

- `SL_DEBUG_TIMEOUT_MS` 默认值。
- 本地 `debug-runs/` 的保留数量和总大小上限。
- dmesg 命令边界快照是否足够捕获 VPU/SHM 瞬时错误。
- `page_nav` 的目标 Activity 完成判据是否需要更细的日志钩子。

## 验收口径

### 每次落地的可检查条件

| 落地步骤 | 完成条件 |
|---|---|
| 内容身份模型与 session 字段 | 视频、直播、动态各能打出一条完整 `content start`，字段与本文一致 |
| UI → compat → daemon 透传 | 同一次播放的 UI/compat/daemon 日志可用同一 `run/session/gen/req` 串联 |
| 统一日志字段与脱敏 | 关键事件均有 run/session；日志中无签名 URL、upsig、trid、buvid |
| debug 启动与归档 | 一条命令完成旧日志拉取、前台启动、新日志拉取、dmesg 快照和 manifest |
| 场景命令 | `play` / `seek_forward` / `pause_resume` / `page_nav` 至少四个场景能自动完成并记录 CMD/EVT |
| 新回归脚本 | 脚本只解析统一日志；不再调用已封存脚本；音画结论仍由用户听感/截图确认 |
| 04 文档翻新 | 真机调试章节只保留统一 debug 流程和本文链接 |

### 最终验收

1. 一条 debug 命令可复现指定内容的指定场景。
2. 统一日志里能直接看到内容类型和权威标识，无需 cid/oid 反推。
3. UI、compat、player、audio 的时间线在同一文件、同一 session 下可读。
4. 页面跳转和播放器操作由真实 wiliwili 的 `Intent` / `MPVCore` / debug-only helper 调用产生，不依赖手工点 UI。
5. dmesg 附件可由 run id 和时间戳关联到同一次运行。
6. 日志中不含签名 URL 和敏感查询参数。
7. 新回归脚本只解析这套输出，不依赖已封存的旧脚本。

## 落地顺序建议

具体任务编号和状态以 [00-当前状态与任务.md](00-当前状态与任务.md) 的 D27 为准。建议实施顺序：

1. 内容身份模型与 session 字段定义。
2. UI 侧权威内容日志、extra/meta 透传和 daemon 日志前缀。
3. 敏感 URL 脱敏。
4. debug 启动命令、旧日志拉取、run 归档和 dmesg 快照。
5. 基于 `Intent` / `MPVCore` / debug-only helper 的启动期 debug 控制器。
6. 基于新日志的新回归脚本。
7. 最后整体翻新 `04` 的真机调试部分。
