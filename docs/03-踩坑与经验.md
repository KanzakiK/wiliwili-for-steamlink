# 踩坑与经验

## 一、SLVideo / 同步

- `GetQueuedVideoMS` 是“已提交未上屏”的真实水位：480p 稳态约 **2.1s**，360p 约 **2.7s**，每次运行有浮动。**不能按 300ms 做限流**（会导致每帧等 2 秒、30 秒只播 25 帧）。
- 判断视频“开始上屏”：队列不再创新高（连续 5 帧）；此时已呈现内容 `P = 已提交内容 − 队列`。
- 音频启动：从预缓冲跳过 `P` 毫秒再提交，替代固定 3 秒延迟；固定延迟会因每次上屏耗时不同而时对时错。
- 音频预缓冲满时**等待**，不能丢帧，否则启动后出现内容缺口。
- seek 用“请求 + 应答”交给音频线程，避免跨线程释放 SLAudio stream。

## 二、DASH

- `fnval=16` 返回 `dash.video[]` / `dash.audio[]`；m4s 自包含，FFmpeg mov demuxer 可直接打开。
- 视频选第一个 `codecs` 以 `avc1` 开头；音频选 `bandwidth` 最大。
- 视频/音频两个 URL 要两套 `StreamBuffer + AVIO + AVFormatContext`；音频线程自己解封装。
- 单 URL（360p MP4）仍走单文件路径，音频包由主线程克隆给音频线程。

## 三、cpr / libcurl

- cpr 1.10 需要 libcurl **≥ 7.68**（`curl_mime`、`CURL_PROGRESSFUNC_CONTINUE`）；SDK 只有 **7.26**，直接编译失败。
- 解决：`app/scripts/build-curl.sh` 交叉编译静态 libcurl 7.79.1 到 `~/steamlink-curl`；`app/cmake/FindCURL.cmake`（wiliwili 构建用 `tools/cmake/FindCURL.cmake`）强制使用它，避免链接 rootfs 的 7.26。
- `app/compat/curl/system.h` 是空垫片（7.26 没有这个头；cprtypes.h 已先包含 curl/curl.h）。
- 链接静态 curl 需要补 `-lssl -lcrypto -lz -lrt -ldl`，以及 `-Wl,-rpath-link,$ROOTFS/usr/lib` 解析 SDL2 的 Marvell 私有符号。
- **SDK 的 libssl/libcrypto 没有 SONAME**：FindOpenSSL 用绝对路径链接时，DT_NEEDED 会写成 WSL 的 sysroot 路径，设备上启动直接失败。必须用 `tools/cmake/FindOpenSSL.cmake` 走 `-lssl -lcrypto`，并在链接前用 `readelf -d` 检查 NEEDED 是否都是纯 soname。

## 四、borealis

- **没有 `List` / `ListItem`**；列表要用 `Box + ScrollingFrame + Recycler` 自己组合。
- `pushActivity` 会调用 `activity->createContentView()` 并用返回值**覆盖**内容；Activity 子类必须重写 `createContentView()`，不能在构造函数里 `setContentView()`（否则被置空 → 段错误）。
- **Label 默认可聚焦**；行/卡片里要把内容 Label `setFocusable(false)`，否则焦点停在文字上、出现空蓝框。
- **B 键不会自动返回**；需要在返回项上显式 `registerAction(BUTTON_B, popActivity)`。
- `registerAction` 的回调签名是 `bool(brls::View*)`。
- 列表加载后要 `Application::giveFocus(firstView)`，否则没有默认焦点、按键无反应。
- 资源路径：`BRLS_RESOURCES_DIR="."`，设备上 `resources/` 与二进制同目录；中文用 wiliwili 的 `switch_font.ttf`（8.3MB）。

## 五、wiliwili API

- `get_hots_all` 等 API 内部的 **WBI 取 key 是同步请求**；在 `mainLoop` 之前调用会阻塞首帧（进程活着但画面不出来）。必须放到主循环启动后的独立线程，回调用 `brls::sync` 回 UI 线程。
- `nlohmann/json` 由 borealis 的 extern 头提供，无需单独子模块。
- API 子集：`bilibili.cpp`、`home_api.cpp`、`search_api.cpp`、`video_detail_api.cpp`、`util/http.cpp`、`util/json.cpp`、`util/wbi.cpp`、`utils/number_helper.cpp`。
- 登录、普通视频弹幕、播放记录同步由原版 wiliwili 提供，不另做模块。
- analytics / dlna / live 弹幕 / 下载表情不在当前范围（live 弹幕依赖 `config_helper`）。

## 六、wiliwili 整仓构建 / libmpv 兼容层

- 设备同时带 **SDL2 和 SDL3**（`libSDL3.so.0.5.0`）。UI 必须用 SDL2：wiliwili 的 borealis 只支持 SDL2；SDL3 是 `libSLVideo.so` 的依赖，两者可同时加载（前面播放器 demo 已验证）。
- `find_package(MPV)` 的 FindMPV 会覆盖 `-DMPV_LIBRARY`，要预置 cache 变量 **`MPV_LIBRARY_mpv`** 才能指向桩库。
- libmpv 兼容层的 `mpv_get_property_string` **不能返回 NULL**：`MPVCore::init` 用 fmt 直接打印 `mpv-version`，NULL 会抛 `fmt::format_error: string pointer is null` 并 terminate。
- **borealis 自带的 glad 是桌面 GL 加载器**：GLES2 上下文里它不会加载 GL 3.0 的 FBO 函数，`glGenFramebuffers` / `glBindFramebuffer` 是空指针。进播放页时 `MPVCore::initializeVideo()` 直接调用会 SIGSEGV（gdb 栈顶 `#0 0x0`）。
  - 解决：构建加 `-DMPV_NO_FB=ON`，并在 libmpv 兼容层的 `mpv_render_context_create` 里用 `SDL_GL_GetProcAddress` 补齐 `glad_glBindFramebuffer` 等指针。
  - 视频改由 SLVideo 输出后**仍需保留这段补装**：wiliwili/borealis 的初始化与绘制路径仍会用到这些 FBO 函数；不能因为“mpv 不画视频”就删掉。
- GCC 9.2 的 `std::filesystem` 需要 `-lstdc++fs`，由 `tools/cmake/steamlink-wiliwili-toolchain.cmake` 补上。
- 构建选项：`PLATFORM_DESKTOP` + `USE_SDL2` + `USE_SYSTEM_SDL2` + `USE_GLES2` + `USE_EGL` + `USE_SYSTEM_CURL` + `DISABLE_WEBP`。
- 日志重定向到文件时 borealis 输出按块缓冲：日志停在 34 行不代表卡死，先截图确认画面。
- **透明层**：borealis 默认 `SDL_GL_ALPHA_SIZE=0` 且不透明 clear，会把 SLVideo 视频层完全盖住。补丁：alpha 改 8 + `SL_TRANSPARENT=1` 时 clear alpha 置 0（`tools/patches/borealis-steamlink-alpha.patch`，构建脚本自动应用）。正式运行由兼容层在播放页运行时切换 `SL_TRANSPARENT`；启动脚本绝不设置它，`SL_SPIKE_NO_IMAGES` 只用于早期 spike。

## 七、验证方式（重要）

- **日志会骗人**：stdout 缓冲/驱动日志会让“已经显示的 UI”看起来像卡死；连续重编前先确认画面。
- UI 验证：用 `tools/capture-window.ps1` 截取采集卡窗口 `Capture View 4K`，直接看截图；不要靠日志猜。
- 声音/音画同步：让用户听、确认；程序内 A/V 偏差只作为辅助。
- 主线程在 `gckOS_WaitSignal` 通常是正常的 GPU/渲染等待，不等于死锁。

## 八、设备 / WSL 操作

- 设备 `/tmp` 是 tmpfs，重启即清；正式持久文件放 `/home/apps/bilibili/` 与 `/usr/local/bilibili/`，WSL 临时资源放 `~`。
- 覆盖设备上正在运行的二进制会 `scp: dest open ... Failure`；先传 `xxx.new`，再原子 `mv` 到目标名。
- `/tmp/launch_cmdline.txt` 用一次就被消费；每次启动前重新写入或 scp（模板 `tools/launch-wiliwili.txt`）。
- 通过 SSH 传带空格的单引号命令时，设备端可能只执行第一个词；改用多个未加引号的参数（如 `cat /proc/meminfo`）。
- 启动流程：写 `/tmp/launch_cmdline.txt` → scp → `killall shell`；程序退出后 UI 自动重启。
- 正式启动的 `HOME` 必须是 `/usr/local/bilibili`（由 `tools/steamlink-app/bilibili.sh` 设置），用于持久化 cookie；**不要写成 `HOME=/tmp`**，否则登录态重启即丢。

## 九、OOM 与进程被杀的快速诊断

设备只有约 269MB 内存、无 swap；播放子进程和 UI 同时运行，内存峰值时内核会杀进程。遇到“暂停后不恢复/播放页退出/IPC 断开”，按顺序查：

1. `dmesg | grep -iE "oom|Killed process"`：确认是否被 OOM killer 杀掉。
2. `ps | grep slplayer`：名字带方括号（如 `[slplayer_daemon]`）表示僵尸，父进程未 `waitpid` 回收。
3. `ls -l /tmp/slplayer_vpu.lock`：存在表示上次非正常退出，Dirty Flag 机制按预期工作。

兼容层收到 `IPC 接收断开` 时必须 `waitpid` 打印退出状态；`WIFSIGNALED` + `SIGKILL` 基本就是 OOM。进程被杀与 UI 崩溃是不同故障：前者可由 watchdog 重启 daemon，后者整页退出。

Linux OOM 与 VDEC/SHM 分配失败要分开看：`Killed process ... anon-rss=...` 是 Linux 内存不足杀进程；`shm_driver heap has not enough ... for (51840000) bytes` / `memory_engine_allocate failed` 是 GPU/VPU 共享内存池的大块连续分配失败，不能按 `/tmp` 或进程 RSS 的方式处理。高清片源的 VDEC 小块分配失败也不是 Linux OOM。

真机证据与当时的内存数据见 [02 开发日志](02-开发进度日志.md) 的 D4/D5 章节。

## 十、`/tmp` 是 tmpfs：资源放进去就是占内存

设备上 `/tmp` 是内存盘且不可回收。二进制、资源、测试视频、旧解包目录都不要长期放 `/tmp`；正式部署走 `tools/steamlink-app/install.sh`，测试产物放 `/home/apps/bilibili/` 或及时删除。

快速判断：

```sh
df -h /tmp
grep Shmem /proc/meminfo
du -sk /tmp/* | sort -n
```

`Shmem` 与 `/tmp` 用量对应，就说明内存被 tmpfs 文件占用，而不是进程泄漏。排查时跑 `tools/steamlink-app/memwatch.sh`：

- `wili` 持续上升：UI 侧泄漏（封面纹理、进度条快照、弹幕对象）。
- `daemon` 持续上升：播放侧缓冲（音频预缓冲、帧队列）。
- `Shmem` 上涨：又有人往 tmpfs 写东西。

`install.sh` 已加入 `/tmp` 占用体检（超过 10MB 告警）。88MB 测试残留导致 OOM 的原始现场见 [02 开发日志](02-开发进度日志.md)。

## 十一、SPS 参数改写与视觉判定

- B 站部分 720P DASH 码流声明 `refs=7 / reorder=4 / buffering=7`。早期曾把“播放约 50 帧后 `SLVideo_GetQueuedVideoMS` 卡死”归因于高 refs，但干净 VPU 基线下同一码流正常播放，说明 `refs=7` 本身不是根因。
- 改 SPS 参数来解决 VPU/SHM 问题走过两次弯路：`4/3/4` 因压缩重排窗口造成花屏/抽动；后来“只降 refs，`reorder/buffering` 保持 7”也在用户多视频真机复测中出现真实花屏。中途一张疑似花屏截图后来确认是视频自身转场特效，不能用单张截图下结论；但后续多视频复测确认花屏真实存在。
- **最终规则：SPS 改写默认关闭。** `SL_SPS_REWRITE=1` 只作受控实验，`SL_SPS_TARGET` 只指定实验目标。VPU/SHM 稳定性靠减少重复 `FreeStream/CreateStream`、连续重建至少间隔 400ms、窗口外 seek 走 HTTP Range 重定位处理，不靠改片源参数。
- 视觉异常必须以用户多视频确认或连续截图为准；日志只能证明“发了改写命令”，不能证明画面正确。测试 SPS 实验前必须恢复干净 VPU 基线（`reboot -f` 后放已知正常流），同一片源、同一清晰度对照，失败即恢复默认。
- 每文件元信息日志中的 `SPS target/need/rewrite` 用来关联现场，不是视觉正确性的证据。完整反复过程见 [02 开发日志](02-开发进度日志.md) 的 SPS 归档章节。

## 十二、mpv 属性初值与 UI 真值

- libmpv 兼容层的属性缓存存在，不等于 wiliwili 已经收到。注册 `mpv_observe_property` 时必须立即回放当前缓存值，且 `PROPERTY_CHANGE` 的 `reply_userdata` 要来自观察表。
- wiliwili 的 `MPVCore::video_speed` 默认是 0；若兼容层不发 `speed=1` 初值，`DanmakuCore` 播放分支的位置计算乘 0，滚动弹幕不动；暂停分支不乘倍速，所以表现为“暂停能看见滚动弹幕、播放只剩固定弹幕”。这是 D7 的最终根因，不是 `core-idle` 事件时序问题。
- 播放按钮图标读的是 `core-idle` 驱动的 `MPV_IDLE → refreshToggleIcon()`，不是 `pause` 属性本身。pause/resume 必须同时更新 `pause` 与 `core-idle`，否则按钮和弹幕分支会得到互相矛盾的 UI 状态。
- 自动化回归必须断言关键属性初值（至少 `speed=1.0`）；仅看命令是否被发送无法发现“缓存有值但 UI 没收到”的问题。

## 十三、图片纹理缓存的内存账

- wiliwili 的 `ImageHelper` 桌面图片后缀默认 `672x378`（横图）、`312x420`（竖图）、`96/160`（头像）、`540`（评论图）；图片下载后解码为 RGBA，再创建 GL 纹理，CPU 临时缓冲会释放，纹理缓存持的是 GPU 纹理。
- RGBA 纹理按 4 字节/像素估算：`672x378` 约 0.97MiB/张，`320x180` 约 0.22MiB/张；`texture_cache_num=100` 满缓存时，单横图类型可差约 75MiB。该数值是上界，实际缓存混合了头像、评论图和封面，但比例足以说明请求尺寸比缓存数/线程数更值得调。
- 降低请求尺寸只改 URL 后缀，不改布局或控件样式；图片会由 GL 缩放到显示区域，需在真机确认清晰度可接受。图片线程和播放器内存缓存已是设置下限，不能继续从设置项省内存。

## 十四、从 SSH 启动 wiliwili 必须走主菜单 handoff

- 不要在主菜单 `shell` 还活着时用 `nohup bilibili.sh` 直接拉起 wiliwili。这样 `shell` 与 wiliwili 会同时存在并抢焦点，真机表现为每次操作闪一下 shell 画面，退出播放时视频继续播放直到进程崩溃。
- 正确做法与点主菜单图标一致：写入 `/tmp/launch_cmdline.txt`，然后 `killall shell`；`shell.sh` 的 while 循环会在 shell 退出后 `eval` 该命令启动应用。启动完成后检查进程表应只有 `shell.sh`、`wiliwili`、`slplayer_daemon`，不应再有 `shell`。
- 正常退出播放的日志必须有 `[mpv-compat] cmd: stop` 和“透明关闭（UI 恢复不透明）”，随后 daemon 才退出。若只有 `控制连接断开` 而没有 `cmd: stop`，先检查是否存在双 UI 抢焦点，再谈播放器退出链路 bug。

## 十五、`VideoView already register MPV Event` 是 UAF 前兆

- 该日志只来自 `VideoView::registerMpvEvent()` 的重复注册分支。`brls::Event` 用 `std::list` 迭代器作订阅句柄；重复 `subscribe()` 会覆盖 `eventSubscribeID`，旧订阅残留在 `MPVCore` 事件链表中并持有已析构的 `VideoView` 指针。
- 典型前兆是 `VideoView set fullscreen state: false` 紧跟这条 error，随后退出时没有 `cmd: stop`、进程静默崩溃。上游 [PR #692](https://github.com/xfangfang/wiliwili/pull/692) / issue #658 已给出完整修复：重复注册直接 `return`，并用 `shared_ptr<bool> aliveToken` 让残留回调在对象析构后变成空操作。
- 本项目已通过 `tools/patches/wiliwili-video-view-event-uaf.patch` 回移该修复。若再见到这条 error，先确认补丁是否被应用；只加 `return` 不做 `aliveToken` 兜底不算等价修复。

## 十六、隐藏控件与焦点导航

- borealis 的 `Box::getDefaultFocus()` 会递归子节点但不检查父容器 visibility；`SliderCell::getDefaultFocus()` 又直接返回内部私有 `pointer`。因此把整块区域或外层 cell 设成 `GONE` / `setFocusable(false)` 后，内部 slider 仍可能接收焦点。隐藏滑杆区域必须同时取消每个内部子控件（pointer）的焦点能力。
- 普通 `brls::Label` 的 `getDefaultFocus()` 会检查自身 visibility，隐藏即可去掉焦点。但如果在别处对它调用了 `setCustomNavigationRoute()`，就不能再 `setFocusable(false)`，否则 borealis 抛 `std::logic_error: Only focusable views can have a custom navigation route`。
- 不要在用户正在播放测试时 `kill -9` 进程来部署/重启。这样会留下 VPU 脏状态和上一视频残帧，后续任何播放都可能闪退；必须先协调停止测试，必要时 `reboot -f` 恢复基线，再通过 `/tmp/launch_cmdline.txt` + `killall shell` 正规 handoff 启动。

## 十七、NaN 几何与诊断环境变量

- wiliwili 详情页加载期 `getRealDuration()` 可能为 0。若直接计算 `playback_time / duration` 得到 NaN，再传给 `nvgRect()` 作宽度，Vivante GLES2 上可能把非法路径填成整屏（现场是与关注按钮同色的粉色），而不是简单丢弃。所有几何尺寸都要先保证 duration>0、finite，再钳制范围；本项目由 `tools/patches/wiliwili-bottom-bar-nan.patch` 处理底部进度条。
- 排查视觉异常时，变量名/主题键名带 `color` 的赋值应优先列为嫌疑对象；即使它看起来只用于 2px 的小矩形，也要继续检查传给几何 API 的宽高是否可能 NaN/Inf。D20 第一次排查就是因为只看到“2px”而提前排除 `bottomBarColor`，多绕了几轮诊断。
- 不要把 `export SL_SPIKE_NO_IMAGES=1` / `SL_TRANSPARENT=1` 这类诊断变量直接写进 `/tmp/launch_cmdline.txt`。`shell.sh` 用 `eval` 执行，变量会留在 shell.sh 环境里，用户从主菜单重启后仍生效，导致预览图消失或 UI 全程透明。诊断后必须重启 shell.sh 或 `reboot -f` 清环境；正式启动命令只写 `/home/apps/bilibili/bilibili.sh`。
