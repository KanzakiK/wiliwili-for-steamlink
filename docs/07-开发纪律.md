# 开发纪律（项目级通用）

> 适用于本项目的**所有**任务（不只是 VPU 鲁棒性）。本文件只写通用纪律；历史复核表、真机数据、回归结果和提交拆解范例都写在 [02 开发日志](02-开发进度日志.md)。
>
> 上下文丢失或接手新任务时，先读这里的三条纪律，再读 [00-当前状态与任务.md](00-当前状态与任务.md)。

## 纪律一：落地前复核真实代码与预想的差异

**核心**：不凭讨论印象、文档描述或平台类比写实现；改代码前回到真实代码 / SDK / 头文件核对。

1. 改代码前先读对应文件，确认**当前**实现与文档描述（行号、调用顺序、函数名、结构体字段）一致；不一致先修正文档，再改代码。
2. 每发现一处"预想 vs 真实"的差异，追加到 [02 开发日志](02-开发进度日志.md)，说明对落地方案的影响——**差异本身往往就是 bug 的线索**。
3. 涉及 SDK / 硬件能力的判断，以本机 SDK 头文件与真机行为为准，不以其他平台（Kodi / Moonlight / 其他 SoC）类比为准。
4. 数值型参数（延时、超时阈值、重试次数、宽限期）**不在文档里凭空拍板**，一律标注为待定，靠真机对照实验确定后回填；先写保守默认值并注明"待校准"。

## 纪律二：落地后做回归测试，不凭日志下结论

**核心**："能跑一次"不算验证；要在整个生命周期内反复循环，验证不产生退化或脏状态。

1. **基线先行**：每轮测试前先确认干净基线（VPU 相关场景先 `reboot -f` → 放已知正常流）。基线不干净之前，所有结论无效。
1. **产物来源先行**：部署和场景测试前核对本地 build 目录的 `CMAKE_HOME_DIRECTORY` 指向当前仓库；`install.sh` 不会重新编译，旧 CMake 缓存可能把过期二进制部署到设备。
2. **分层回归**：单操作循环 → 完整生命周期循环 → 异常恢复循环 → 长时间浸泡。覆盖正常路径与异常路径（异常退出、父进程死亡等）。
3. **视觉/听觉结论必须取证**：UI、画面、音画同步必须注明"采集卡截图确认"或"用户真机确认"，**不能只凭日志推断**。日志里"提交了 N 帧"≠"画面真的显示了"。
4. 判定标准要具体：出现退化即失败，记录现场（阶段、读位置、队列、刚做过什么操作），回到纪律一复核。
5. 测试结果追加到 [02-开发进度日志.md](02-开发进度日志.md)，架构/状态变化更新 [00-当前状态与任务.md](00-当前状态与任务.md)。
6. **旧用例已封存**：`tools/deprecated-tests/test-3.5c.sh` 与 `compat_test.c` 只保留历史记录，**不得运行，也不得作为任何回归验收依据**。真机曾出现脏环境“有声音无画面”、干净环境“有画面无声音”，脚本 PASS/FAIL 与音视频状态无关；新回归见 [00](00-当前状态与任务.md) 的 D26。
7. **同步类验收**：只在真实 wiliwili 播放页用 `--diag --sync-debug` 抓日志，结合用户真机听感和截图判断；按 [08 设计](08-统一调试与日志系统设计.md) 的内容身份模型识别片源，不反推 BV，`--open-bv` 留下的 `tag` 在切片后可能过期。

## 纪律三：先测试后提交，按主题拆解

**核心**：未经验证的改动不提交；不同关注点的改动不混在一个提交里。

1. **先测试后提交**：改完 → 编译 → 回归测试（含截图取证）→ 通过后才 commit。不允许边写边提交。
2. **按逻辑主题拆解**：一次落地的改动按关注点拆成多个独立提交（架构设计 / 代码实现 / 进度记录分开），每个提交单一主题，不混提交。
3. **拆解粒度以"能独立编译"为准**：若同一步骤的改动交织在同一文件的相邻位置（拆开会产生编不过的中间提交），允许合为一个主题提交，但要在 commit message 里分段写清；不同文件类型的关注点（文档 vs 代码）必须拆开。
4. **提交消息用项目风格**：中文描述 + 明确的主题标注，例如 `feat(slplayer): VPU 生命周期防御与检测接口`。
5. **内部目录不入库**：`.workbuddy/` 是工作区记忆目录，绝不提交；用明确的 `git add <文件>` 添加，不用 `git add -A`。

## 纪律四：任务只写在 00（单一任务看板）

**核心**：[00-当前状态与任务.md](00-当前状态与任务.md) 是**唯一**的任务看板；其他文档只记录事实、决策、开发记录，不维护任务清单。

1. 任务清单、当前阶段、下一步、验收标准、阶段编号——全部只在 `00`，不在其他文档散落。
2. 专题文档只写边界、接口、结构和机制契约；真机结果、过程记录和历史结论写 `02`，不写"下一步做 X""第 N 步待办"这类任务分派。
3. 阶段编号和任务编号统一在 `00` 定义，其他文档引用任务时指向 `00`，不自行编号。
4. 阶段结束：更新 `00` 的任务状态 + 在 `02` 追加开发记录，然后按纪律三提交。

## 纪律五：诊断能力要积累，按启动参数开启

**核心**：诊断代码不是一次性脚手架。定位完成后只关闭开关，不删除代码；调试能力必须逐轮积累。

1. 新增诊断默认关闭，由环境变量或启动参数控制；正式启动脚本不默认开启。
2. 诊断日志只进入 `/tmp/wiliwili.log`，启动时由 `wiliwili.sh` 清空；长期浸泡若开启诊断，需关注 tmpfs 占用。
3. 启动入口统一解析调试参数：`--diag`、`--sync-debug`、`--http-debug`、`--stop-debug`、`--diag-all`，也支持同名环境变量；调试参数不得传给 wiliwili 本体。
4. 每次新增诊断开关必须写进 [04 构建与真机调试](04-构建与真机调试.md)，说明输出内容、开启方式、性能与日志成本。
5. 定位结束后撤掉的是“默认开启”和过高的日志频率，不是源码中的 env-gated 诊断能力。

## 纪律六：设计未收敛时先讨论，不急着改代码

**核心**：用户提出疑问、猜想、方向性意见或还在比较方案时，先讨论清楚，不把“深入分析”自动变成源码改动。

1. 这类消息默认只做只读取证、真实代码核对、方案取舍和风险说明，不改源码、不部署、不重启。
2. 明确收到“改 / 修 / 开始 / 部署 / 提交”等执行指令后再落地；不确定时先说明方案并等待确认。
3. 文档可以记录刚确认的事实和拍板结论，但不能把未拍板的设计写成已实现状态。
4. 讨论期间可以主动发现新问题，但先讲清证据与影响，不顺手夹带无关修复。

## 纪律七：代码与计划冲突时先取证再拍板

**核心**：计划是设计假设，真实代码、SDK 和真机行为才是事实；不能为了让实现看起来符合计划而静默改计划，也不能让代码偏离已拍板契约。

1. 文档事实错误：代码/SDK 证据明确且设计意图不变，改文档、不改代码，并在 [02 开发日志](02-开发进度日志.md) 记录文件、行号和证据。
2. 实现偏离契约：默认改代码回到契约；若契约本身不可行，先停止并列出候选方案。
3. 真机结论推翻假设：以截图、日志和用户听感为准，暂停相关实现，更新设计后再继续。
4. 用户拍板：接口、session 字段、IPC 格式、debug 参数、正式包边界、默认行为、脱敏规则和验收标准。实现者可自行决定不改变契约的局部实现细节。
5. 涉及 IPC 契约、正式包 debug 行为、敏感参数回写、绕开上游 `Intent`/`MPVCore` 调用链时，必须先确认，不能静默兼容。

## 纪律八：场景测试必须从统一 debug 入口触发

**核心**：启动流程是测试触发条件的一部分。用户通知“测试某场景”时，必须按 [08 设计](08-统一调试与日志系统设计.md) 的统一入口启动，不能用手工 UI 操作冒充自动化场景结果。

1. D27 落地后，场景测试统一使用 `tools/steamlink-app/debug.sh --content ... --scene ... --arg ...`；由入口生成 run id、归档统一日志和 dmesg 附件。
2. 第一版只有启动期场景，不支持运行中命令通道；进入应用后再手工点 UI、从主菜单启动或手工写 `/tmp/launch_cmdline.txt`，都不算按场景测试。
3. 若确需临时手工探索，必须先说明“这是手工探索，不是场景回归”；结果不能写入自动化验收结论。
4. 场景报告必须附 run id 和统一日志；缺少 run id 的结果只能作为现场观察，不能作为 D26/D27 验收依据。
5. 测试启动流程与 08 契约冲突时，按纪律七先取证、拍板并记录，不能临时改启动方式继续跑。
