> 目标：在 Valve Steam Link 硬件盒子上移植/新写一个能看 B 站的原生客户端

| 许可证 | 项目整体 **GPL-3.0** 开源 | wiliwili / ThirdBili / MELODY PSP / Kodi 都是 GPL，天然一致，不存在被迫重写的风险 |

## 一、历史对话摘要

这几轮对话从一个简单问题开始，逐步演进成一个完整的移植规划。记录脉络和**被纠正的错误认知**（后者尤其重要，避免重蹈覆辙）。

### 对话演进

1. 用户下载了 `qiin2333/moonlight-qt` 的两个 release 包，问 Steam Link 版怎么装、是否需要双公头线。
2. 澄清了两个包的区别、U 盘安装法、Steam Link 硬件规格、第三方系统玩法。
3. 深入讨论解码延迟测量方法（Moonlight 统计层 / 240fps 高速摄影）。
4. 处理 U 盘：Ventoy 清掉 → MBR+FAT32 格式化 → 解压 Moonlight V+ 进去（已完成）。
5. 盘点 Steam Link 可装的第三方 app（Kodi / RetroArch / MAME4ALL 等）。
6. 探讨"移植 wiliwili 到 Steam Link 是否可行"——这是本次规划的核心线索，经过多轮查证与反复纠错。
7. 用户决定自己动手写客户端，讨论架构选型，最终确定"三源拼装"方案。
8. 用户开始接硬件、开 SSH、验证环境，准备开工。
9. 文档自检阶段补充了 3DS/PSP 的网易云客户端项目（ClouDS Music / MELODY PSP），发现其线程模型、边下边播、验证流程有很高复用价值，且 MELODY PSP 含 MV 视频播放 + AVC 硬解。

### 关键纠错记录（重要）

这一路的结论多次被用户质疑并推翻，最终版才是正确的。**以下"❌ 错误认知 → ✅ 事实"要牢记**：

| # | ❌ 曾经的错误说法 | ✅ 查证后的事实 |
|---|---|---|
| 1 | 装 Steam Link app 需要双公头 USB 线 | 用 U 盘即可，双公头线是刷第三方系统/救砖的说法，且常规也不需要 |
| 2 | wiliwili 需要 OpenGL 3.2，Steam Link 只有 GLES2，是硬伤 | wiliwili 官方支持 OpenGL2/ES2/ES3（`-DUSE_GLES2=ON`），PSV/PS4 版就是 GLES2。图形 API 不是障碍 |
| 3 | SLVideo 是 Moonlight 作者跟 Valve 合作才拿到的私有库 | SLVideo 是 Steam Link SDK **公开**的一部分，`rootfs/usr/include/SLVideo.h` + `libSLVideo.so`，Valve 2016 年署名，zlib 类许可证允许商用 |
| 4 | Kodi 移植走 FFmpeg 软解，没接 SLVideo | Kodi 早在 **2017 年 1 月**就提交了完整的 SLVideo 硬解实现（`CDVDCodecs/Video/steamlink/` + `RendererSteamLink` + `AESinkSteamLink` 一整套，约 25 个文件），比 Moonlight 接入（2019）早两年 |
| 5 | 256MB 可用内存是移植的硬瓶颈 | 3DS 只有 128MB RAM（New 3DS 256MB）照样跑 B 站客户端 360P/480P。内存不是决定性障碍 |

**根本教训**：多次把"听起来合理的技术障碍"当成结论，没查到底。用户每次较真都推动查到更深的源码级证据。最终结论是——**技术上没有原理性障碍，没人做纯粹是因为盒子停产、社区散了、收益太低**。

### 支持这个结论的关键证据

- **PSV 移植存在且是官方支持**：wiliwili 作者 xfangfang 官方支持 PSVita/PS4/Switch，有 `-DPLATFORM_PSV=ON`、官方 release 的 `.vpk`、官方 docker 构建镜像。作者还做了 3DS 的 B 站客户端 `ThirdBili`（同一个作者）。
- **Kodi 已打通全链路**：Kodi 的 Steam Link 移植证明了①依赖链能用 `tools/depends` 交叉编译②SLVideo 硬解能接入③能打成 U 盘 app 包。
- **3DS 项目证明内存不是问题**：`bilibili-3ds` / `3danmu` 在 128MB 内存的 3DS 上实现了推荐流、搜索、扫码登录、360P/480P 播放、滚动弹幕、CC 字幕。

## 二、Steam Link 基本信息

### 硬件规格

| 项目 | 规格 |
|---|---|
| SoC | Marvell DE3005-A1（ARMADA 1500 Mini），1GHz **单核** ARMv7，hard-float ABI，NEON |
| GPU | Vivante GC1000，仅 **OpenGL ES 2.0** |
| 内存 | 512MB DDR3（256MB 系统 + 256MB GPU 分摊）；**实测 Linux 可见 263MB，开机后真正可用约 140~160MB**（见阶段 0 实测） |
| 存储 | 4GB NAND，约 1GB 可用 |
| 网络 | 100Mbps 百兆网口 + 802.11ac 2×2 WiFi + 蓝牙 4.0 |
| 接口 | 3× USB 2.0、HDMI（最高 1080p60） |
| 系统 | 定制 Linux，内核 3.8，glibc 2.19 |
| SDK 支持 | GLES 2.0、Qt 5.14.1、SDL 2.0、GCC 交叉工具链 |

### 安装与调试机制

- **装 app**：FAT32 U 盘，目录结构 `U盘:\steamlink\apps\<appname>\`，插入后重启，系统自动把 app 复制进盒子闪存，主界面出现图标。装完可拔 U 盘。
- **开 SSH**：U 盘放 `steamlink\config\system\enable_ssh.txt`（非空即可），插上重启。
  - 用户名 `root`，密码 `<device-password>`
  - IP 去路由器 DHCP 列表找（别信文档里的示例 IP `10.0.0.103`）
  - SSH 会保持开启直到 factory reset 或移除该文件
- **自动更新**：联网会自动下载固件更新并重启，属正常行为。**更正**：早前记的"固件更新会重置 SSH"是误判——实测 `/mnt/config` 里 2022 年写入的配置文件在升级到 build 930 后依然存在，说明 config 分区在升级中保留；当时 22 端口不通只是因为**此前从未开过 SSH**，与升级无关。详见"阶段 0.5"的持久化实测。
- **调试**：SDK 推荐 gdbserver 远程调试。

## 四、规划架构（三源拼装）

**核心决策：不要移植 wiliwili 本体（mpv 是包袱），而是起一个新工程，从三个项目各取一层。**

```
┌─────────────┐  ┌─────────────┐  ┌─────────────┐
│  wiliwili   │  │ ThirdBili   │  │ Kodi 补丁   │
│ api/presenter│ │ network_    │  │ steamlink/  │
│ view/activity│ │ decoder/system│ │ 硬解/窗口层 │
└──────┬──────┘  └──────┬──────┘  └──────┬──────┘
       │                │                │
       ▼                ▼                ▼
┌──────────────────────────────────────────────────┐
│                  你的新工程                      │
│  UI + B站业务  ← wiliwili                       │
│  播放管线      ← ThirdBili                      │
│  SLVideo 硬解  ← Kodi                           │
│  平台抽象      ← ThirdBili system/ 分层思路     │
└──────────────────────────────────────────────────┘
```

### 模块映射表

| 模块 | 来源 | 改动点 |
|---|---|---|
| B 站 API / 扫码登录 / 弹幕数据 / 评论 / 推荐 | wiliwili `api/` `presenter/` | 基本不动，可能精简字段 |
| UI 渲染（nanovg + borealis） | wiliwili `view/` `activity/` | `-DUSE_GLES2=ON -DUSE_SDL2=ON`，按键映射改 Steam Link 手柄 |
| 播放管线（解封装 + 缓冲 + 异步） | ThirdBili `network_decoder/` | MVD 调用换成 SLVideo，分辨率上限 360p→1080p |
| 硬解封装 | Kodi `DVDCodecs/Video/steamlink/`（6 对文件）+ `RendererSteamLink` | 基本不动，剥掉 Kodi 的 `CVideoBuffer` 依赖即可 |
| **窗口 / GL 上下文（GUI 怎么叠在视频上）** | Kodi `windowing/steamlink/`（`WinSystemSteamLink` + `GLContextEGL`） | **重点参考**：它用 SDL 窗口 + EGL/GLES2 叠在 SLVideo 视频之上，是本项目"弹幕/UI"的可行性依据 |
| 音频输出 | Kodi `AudioEngine/Sinks/steamlink/AESinkSteamLink*`，或直接用 SDL2 Audio | 先用 SDL2 Audio 最省事，SLAudio 作备份 |
| 平台抽象（输入/存储/设置） | ThirdBili `system/` | 换成 Steam Link SDK 的 SDL2 + 文件系统路径 |

### SLVideo API 关键约束（逐条对过头文件，写代码前必看）

| 约束 | 对代码的影响 |
|---|---|
| `k_ESLVideoFormatH264` 是**唯一**格式 | B 站只能选 H264 流，必须避开 AV1/HEVC/AVS |
| `bLowLatency != 0` 只支持 I/P 帧 | 点播用 `bLowLatency=0`（可吃 B 帧）；低延迟模式是给 Moonlight 串流用的 |
| 码率上限约 30000 kBit/s（30 Mbit/s） | 头文件原话 "approximate bit rate limit of about 30000"；B 站高码率 1080P 必须压 |
| `SubmitFrame` 后硬件自动上屏，**没有 seek 接口** | 进度条拖动 = `FreeStream` 重建 stream + 从关键帧重喂 |
| 三个关键函数都返回 int，要看返回值 | `BeginFrame` 返 -1 = 宏块错误或**解码器跟不上**（天然的背压信号，据此暂停取流）；`WriteFrameData` 写超返 -1；`SubmitFrame` 出错返 -1 |
| `GetQueuedVideoMS` 对低延迟流恒返回 0 | 别指望它做点播缓冲水位统计，自己算 |
| overlay 同时只能显示 **1 个** | 多个 overlay 只能"轮流 show"模拟多缓冲，不是多层叠加 |
| **overlay 与 GUI 窗口抢同一个硬件 overlay 平面** | 本项目最大的坑，详见下一小节 |

**⭐ 图层结论（2026-11-16 读 Kodi 补丁 + Moonlight 源码后确认，红灯②的关键答案）**

Steam Link 的显示栈大致是「**视频层**」+「**overlay 平面**」两层：视频由 SLVideo 硬件解码直接出图，而 GUI 窗口和 SLVideo 自己的 overlay 都挂在同一个 overlay 平面上。三个实测/源码级事实：

1. **Kodi 一行 SLVideo overlay 代码都没写**（4146 行补丁里搜不到 `SLVideo_CreateOverlay`），它的菜单、进度条、OSD 全部由 GL 画在 GUI 层，视频照常播放——**说明"GUI 层叠在视频层之上"这条路径走得通**。这就是弹幕该走的路：用 nanovg 画进 GL 层，不用 overlay。
2. **Moonlight 那个 HACK 的真相**：`SLVideo_CreateOverlay` 会改变 overlay 平面的尺寸，导致 Qt 的 GUI 被"压扁"成 WxH 的区域。所以它建一个满屏 overlay、`Show` 一下立刻 `Hide`+`Free`，把平面尺寸刷回全屏。→ **播放时别随手 CreateOverlay，否则 UI 会变形**。
3. overlay 的像素是**我们自己往内存里填的**（`GetOverlayPixels` 拿指针 + pitch），不是免费的"硬件合成"。1920×1080 ARGB 每帧约 8MB，这颗单核绝对扛不住；真要用就把 surface 做小（`CreateOverlay` 的宽高可与屏幕不同），再用 `SetOverlayDisplayArea` 摆位置——它接受**归一化 0~1 坐标**（Moonlight 实例：`SetOverlayDisplayArea(o, 0.0f, 1.0f - h, w, h)` 贴左下角）。
4. **侧证**：Qt6 补丁里的 marvell mkspec（见「阶段 0.6」存档段）把 EGL 配成 `-DEGL_API_FB` 并链接 `-lEGL -lGAL -lVSC -lshm -lOSAL -lPEAgent` —— 图形和视频合成走的是 Marvell/Vivante 这套私有栈（GAL 是 Vivante 的图形抽象层），不是应用层自己混叠。这与"两个平面由底层合成"的判断一致。

**核心 API 调用序列**：`SLVideo_CreateContext()` → `SLVideo_CreateStream(ctx, k_ESLVideoFormatH264, /*bLowLatency=*/0)` → 每帧 `BeginFrame(n)` / `WriteFrameData(p, n)` / `SubmitFrame()` → `FreeStream` / `FreeContext`。可选：`SetStreamTargetBitrate` / `SetStreamTargetFramerate` / `SetStreamVideoTransferMatrix`。overlay 侧：`CreateOverlay` / `GetOverlayPixels` / `SetOverlayDisplayArea` / `ShowOverlay` / `HideOverlay` / `FreeOverlay`。

### Kodi 硬解实现文件清单（补丁里的 4146 行，按目录分组）

**视频解码（核心，直接复用）** `xbmc/cores/VideoPlayer/DVDCodecs/Video/steamlink/`
- `SteamLinkVideo.cpp/.h` — 解码器主体，注册为 CDVDVideoCodec（约 515 行，最值钱的一个文件）

### 阶段 0.5：SSH 与调试工作流（实测踩通，非常重要）

**开 SSH 的正确姿势（实测有坑）：**

```sh
# U 盘 FAT32 根目录放：
steamlink/config/system/enable_ssh.txt      # 必须非空（写个字符即可）
```

- **必须彻底断电冷启动**（拔电源线），**菜单里的"重启"不生效**——实测菜单重启那次没读到 U 盘，冷启动立刻就通了
- 固件 `S01config` 里找 U 盘只有约 **2 秒窗口**（`for i in seq 4` + `sleep 0.5`），且**只探测 `f7ee0000.usb` 一个控制器**——插错 USB 口会永远扫不到。**用第一次成功装过 app 的那个口**最稳
- 密码 `<device-password>`，**密码认证在 build 930 上是可用的**（网上有说新固件禁了密码认证，本机实测没有）
- SSH 起来得比 UI 还早：开机画面还没走完，22 端口就已经能连了
- 若 `ping` 通但 22 不通，先确认 IP 没变：查 ARP 里 MAC 是否为 Valve 的 OUI（本机是 `e0:31:9e:*`，属 Valve Corporation）

**⭐ SSH 是持久化的——只插一次 U 盘，之后不用再插（2026-11-16 实测确认）**

`enable_ssh.txt` 在开机时被 `S01config` 从 U 盘 `cp -r` 到 **`/mnt/config/system/`**，而 `/mnt/config` 是 **NAND 上的 yaffs2 持久分区**（`/dev/block/mtdblock3`，512MB，只用了 15MB），不是 tmpfs：

| 证据 | 结论 |
|---|---|
| `mount` 显示 `/dev/block/mtdblock3 on /mnt/config type yaffs2 (rw)` | 真实闪存分区，重启不丢 |
| `S30sshd`：`if [ -f /mnt/config/system/enable_ssh.txt ]; then ... /usr/sbin/sshd; fi` | 每次开机只要文件在就自动起 sshd |
| `grep -rn "enable_ssh" /etc /usr` **只命中 S30sshd 一处** | 全系统没有任何删除/消费该文件的逻辑 |
| init 脚本里**没有**格式化 mtdblock3 的操作（只有 `apps.img` 的 ext4 会在缺失时 mkfs） | config 分区不会被开机流程重建 |
| 分区里还留着 `wifi_band_selection.txt`(2022-04)、`display_scale.txt`(2022-05) | 连固件升级都没清掉它 |

**所以标准流程是：插 U 盘冷启动一次 → 启好后把 U 盘拔掉即可，之后每次开机 SSH 都在。**
恢复出厂（U 盘放 `factory_reset.txt`）或极少数大版本升级才可能需要重来一次。

> ⚠️ **U 盘这条路的破坏性提醒（已处理，但规律要记住）。**
> `S01config` 对 `steamlink/apps/*` 的处理是 `rm -rf ${appdir}` 然后 `cp -r`——**只要开机时插着 U 盘，`/home/apps` 里同名 app 就会被无条件删掉重装**。当初插着装 V+ 6.5.5 时，就是这么把能用的版本覆盖成坏包的。
> 现状（2026-11-16 已处理）：U 盘的 `steamlink\apps\moonlight` 已换成**官方 6.2.0**，插回开机只会重装同一个可用版本；`config\system\enable_ssh.txt` 保留。
> **日常开发不要再靠 U 盘**——SSH 推文件秒级完成，U 盘只在首次安装或恢复出厂后用。

**⭐ 关键工作流：不用再插拔 U 盘了**

有 SSH 之后，装 app / 换二进制全部可以直接推，秒级完成，`/home/apps` 是 loop 挂载的 ext4 镜像，可直接写：

```sh
# 本地目录 → 设备（比 scp 稳，不依赖 sftp-server）
tar cf - . | ssh root@<ip> 'mkdir -p /home/apps/<name> && tar xf - -C /home/apps/<name> && chmod -R +x /home/apps/<name>'
```

调试同理：直接从 SSH 启动 app 并读日志，比对着电视猜快得多。

```sh
cd /home/apps/moonlight && (sh moonlight.sh >/dev/null 2>&1 &) ; sleep 15
tail -40 /tmp/moonlight.log
```

注意 `/tmp` 每次重启清空，**日志必须在同一次开机会话里读**。

**实测发现的三个坑（写代码前必看）：**

1. **SLVideo 依赖 SDL3，不只 SDL2**：SDK 的 `libSLVideo.so` NEEDED 里有 `libSDL3.so.0`、`libPEAgent.so`、`libOSAL.so`、`libshm.so`。设备 build 930 的 `/usr/lib/libSDL3.so.0` → 0.5.0，全部可解析。**链接时必须带 `-Wl,-rpath-link,$ROOTFS/usr/lib -Wl,-rpath-link,$ROOTFS/lib`**，否则会报几十条 undefined reference（库其实都在 sysroot 里，只是 ld 找不到）。
2. **SDK 里的 SLVideo/SLAudio 与设备固件不是同一份**：md5 分别为 SDK `fdb881…`/`e662da…` vs 设备 `ff58f9…`/`e2516b…`。实测 ABI 兼容（上下文创建正常），但最终验收以设备库为准。
3. **`SLVideo_CreateContext()` 会初始化 Vivante/EGL 显示**：日志显示它创建 1280x720 帧缓冲并缩放到 1920x1080。阶段 1.4 做「GL 层叠视频」时要安排初始化顺序，不能假设 SLVideo 只碰视频平面。

**其它小坑**：WSL 的 `/tmp` 在发行版停止后清空，测试文件放 `~/`；设备的 BusyBox `timeout` 不支持 `timeout 10 cmd` 写法；`nasm` 未装（ARM 交叉编译 FFmpeg 不需要）。

- JSON 用轻量字段提取（`json_find_key` + 字符串/数字），不引入第三方库
- 真机结果：热门视频 `BV1Uesp6yEsM`（cid 43627448897）端到端播放 30 秒，**画面/声音正常**；RSS 28.7MB、CPU 11.9% 单核

**✅ 阶段 2.3d 缓冲窗口化 + 音画同步（2026-11-16）**

- 注意：3000ms 是当前"kill UI + 独立 app + 电视 HDMI 重同步"流程下的值，最终常驻 UI 方案可能只需几百 ms，不能直接当常量
- 待办：播放控制、480p DASH、WBI 兜底

**✅ 阶段 2.3e 播放控制（2026-11-16）**

**✅ 阶段 2.3f 播放线程化 + 自动音画同步（2026-11-16）**

- 480p 诊断结论：480p AVC（852x480@30）+ AAC 44.1kHz 本身能解，`BeginFrame` 重试 0，**不是解码器背压**；瓶颈是单线程主循环同时做"FFmpeg 解封装 + AAC 解码 + 44.1→48k 重采样 + 视频喂帧 + 手柄/进度条"，30fps 预算不够。`GetQueuedVideoMS` 从 200ms 一路涨到 2130ms，后半段卡顿并逐渐音画失步（音频领先）。
- 已完成的重构：
  1. AAC 解码 + 重采样 + SLAudio 提交移到**独立音频线程**；主线程只把音频包 `av_packet_clone` 进有界包队列（96 包 / 4MB，满则反压解封装）。
  2. 音频线程用预缓冲承接启动；`SLAudio_GetQueuedAudioSamples` 限深约 200ms，避免解码跑太快丢帧；seek 用"请求 + 应答"交给音频线程执行，避免跨线程释放。
  3. 视频主线保留单调节拍；`GetQueuedVideoMS` 只做 4 秒失控保护（实测正常水位 1.5~2.7s，**不能当 300ms 水位用**）。
- **自动音画同步（关键修复）**：固定延迟不可靠——视频上屏耗时每次运行在 1.5~2.7s 之间浮动，加大固定延迟反而可能更领先。改为：
  1. 每帧记录"已提交的最大 PTS"和 `GetQueuedVideoMS`（官方注释：submitted but not presented）。
  2. 队列不再创新高（连续 5 帧）判定视频开始上屏；此时已呈现内容 `P = 已提交内容 - 队列`。
  3. 音频启动时从预缓冲跳过 P 毫秒，使音频内容与画面内容对齐；`--audio-delay N` 可退回固定延迟做对照。
- 程序内 A/V 偏差（音频已播内容 − 视频呈现内容）：480p 全程 ±100ms 量级，360p 网络流 ±200ms 内；**无累积漂移**。B 帧/GOP 采样会带来 ±300ms 量化噪声。
- 真机结果：
  - 480p 本地合流（30.13s）：904 帧完整播完；上屏判定 2.53s、跳过 371ms；`BeginFrame` 重试 0；RSS 10.1MB、CPU 13.6% 单核。
  - 360p 网络流（`--popular` 30s）：742 帧；上屏判定 3.2s、跳过 507ms；音频包队列满 96（正常反压）；RSS 19.4MB、CPU 16.2% 单核。
  - 用户确认 480p 自动同步版"基本同步"。
- 已知限制：启动时最多丢掉 0~0.5s 音频；seek 后仍用 300ms 固定延迟（显示管线已热）。
- 下一步：DASH 双流（视频/音频两个 URL，各自 StreamBuffer/AVIO/AVFormatContext）。

**✅ 阶段 2.4 480p DASH 双流（2026-11-16）**

- `playurl` 改用 `fnval=16`：`dash.video[]` 取第一个 `codecs` 以 avc1 开头的条目，`dash.audio[]` 取 bandwidth 最大的条目；拿不到 DASH 时自动回退 `fnval=1` 单文件 MP4（360p）。
- 新增 `MediaSource`：每个 URL 一套 StreamBuffer（8MB 窗口）+ 自定义 AVIO + AVFormatContext。视频由主线程解封装；音频线程自己解封装独立音频流，不再经过主线程的包队列。
- seek：主线程对视频 `av_seek_frame`；音频线程收到请求后对自己的 format 跳转并 flush/重建 SLAudio。
- 修复：音频预缓冲满时原来直接丢帧，会在启动后造成内容缺口；改为等待，并在启动时刻立刻醒来（避免等待与启动判定死锁）。
- 真机结果（`--popular 30`，640x480@25 AVC + AAC 48kHz）：
  - 737 帧完整播放，`BeginFrame` 重试 0；音频预缓冲 10.92s、跳过 0.34s 启动
  - A/V 偏差全程在 ±223ms 内（25fps/GOP 量化噪声），无累积漂移
  - RSS 27.6MB（两路 8MB 窗口）、CPU 16.2% 单核
- 待确认：用户听感；DASH 模式下 ±10s 跳转；长视频回跳仍受窗口限制。

### B 站视频流格式问题（重要坑）

B 站 API 返回的视频流（flv/mp4 封装）里的 H.264 是 **AVCC/avcC 格式**（带长度前缀），而 SLVideo 需要的是 **Annex-B 格式**（`00 00 00 01` 起始码）。喂错格式会直接解码失败。

- 好在 Kodi 补丁里已经写了转换实现：`SteamLinkVideo.cpp` 里标注 `based on h264_mp4toannexb_bsf.c (ffmpeg)` 的几段代码（约在补丁 2042、2109、2173 行），直接复用。
- FFmpeg 侧用 `h264_mp4toannexb` bitstream filter 也能做转换。

### 音频方案

- SLVideo 只管视频，**音频要自己处理**。
- 两个选择：① SDK 提供的 `SLAudio`（13 个 API，`CreateInputStream` → `BeginFrame`/`SubmitFrame`；Kodi 的 `AESinkSteamLinkStream.cpp` 是完整用法参考）；② SDL2 Audio（设备自带 SDL2，最省事）。
- 建议：**解封装/解码用 FFmpeg 出 PCM，输出先走 SDL2 Audio**；若听到卡顿或延迟异常，再换 SLAudio（走同一条音频硬件通路，理论上更省 CPU）。
- 阶段 1 的 demo 里就验一次出声，别拖到后面。

### Kodi 依赖交叉编译的实战细节

从 `build_steamlink.sh`（kodi-18 分支）里提炼的可复用经验：

- 用 Kodi 自带的 `tools/depends` 框架：`./configure --with-platform=steamlink --with-toolchain=<SDK>/toolchain --host=armv7a-cros-linux-gnueabi`
- **必须从"干净 shell"构建**，不能 `source setenv.sh`，否则污染原生工具的编译环境（脚本里有检查）
- 有些库复用 SDK 里的（如 alsa-lib），用 `satisfy_dependency` 技巧：编译但不安装，然后 `touch .installed-*` 骗过 depends
- GMP 与 Kodi 冲突，要先在 SDK 里 uninstall 掉
- 有一个 libgpg-error 的 `host_triplet` 需要 sed 手动修正
- 最后 strip 二进制（用 SDK 的 `armv7a-cros-linux-gnueabi-strip`）、拷贝 .so 到 app 目录、写 `toc.txt` + 启动脚本 + 图标，打包成 U 盘 app

### 调试手段

- **看日志**：SSH 进去 `tail -F /tmp/<app>.log`（`/tmp` 每次重启清空，**日志必须在同一次开机会话里读**）

  ```sh

  ```

### 性能预期（别期望过高）

- **wiliwili PSV 版**：官方 Wiki 说硬解"流畅 360P，勉强 720P，480P 效果最差"（作者自己也困惑为什么 480P 更差）；另一个 README 说 720P 横屏流畅、480P 竖屏、部分直播 1080P 原画。综合看，小 ARM 设备上 360P/480P 是甜点区。

### 3DS/PSP 网易云项目可复用的工程经验（2026-11-16 补充）

用户提示后新查的 `ClouDS Music`（3DS）和 `MELODY PSP`（PSP），都是 2026 年 11 月仍在活跃维护的原生网络流媒体客户端。**注意纠正一个直觉：MELODY PSP 不只是音乐播放器——它有完整的 MV（视频）播放管线**，虽是音乐 MV 场景，但"弱硬件上边下边播 + 硬解/软解切换"的工程范式跟我们高度同构。

**1. 线程模型（MELODY PSP，强烈建议照抄）**

PSP 是单核 MIPS，跟 Steam Link 单核 ARMv7 处境一样。它的做法：

- 主线程**只做输入 + 状态机 + 绘制，永不阻塞在网络/文件 I/O 上**（除了极短的 open）
- 独立工作线程：`api`（HTTP + JSON）、`dl`（下载/流）、`dec`（解码→环形缓冲）、`audio`（输出）、`dns`（有界 DNS 解析）
- 线程间用**无锁事件环形队列**（`ApiEvent`）投递结果，主线程每帧 `poll`；事件带 `index` + **请求代次号（generation）**，旧请求的迟到回应不会覆盖新状态——这个细节很关键，网络客户端常见的竞态 bug 就是这么来的
- 共享状态要么全在一个锁里，要么用代次号做乐观校验

**2. 边下边播的"可读前缀"协议（MELODY PSP，可直接借鉴）**

下载线程负责写、解码线程负责读同一个文件，用 `stream_available(gen)` / `stream_readable()` 同步，避免"读方先打开空文件、写方 O_TRUNC 失败"的老问题。MV 起播还有**速率门槛**：实测带宽 ≥ 1.25 × 视频码率才起播，否则继续缓冲并显示"速率/所需带宽/剩余时间"。这套逻辑对 B 站取流直接适用。

**3. 断点续传与进度（MELODY PSP）**

`.part` 记录每片偏移 + 前缀哈希，重连后从原偏移续传不重下；进度一律按**字节数**换算，不用"已写块数/总块数"（后者会出现 100% 却没下完）。

**4. 开发/验证流程（ClouDS Music，值得学的工程习惯）**

- `make host-test`：不用目标硬件也能在 PC 上跑测试；`make emulator-build` 用固定版本模拟器 + 仓库固定 Docker 环境（锁 SHA-256），避免环境漂移
- 仓库有 `AGENTS.md` 写明给 AI/后续开发者的工程约束（遇到可疑需求先验证边界、用 Context7 查最新资料、不机械格式化 vendor 代码、提交前必须 host-test + 模拟器 + 真机三层验证）
- 明确"模拟器不能替代真机"的范围：内存、DSP、睡眠、真实 Wi-Fi、存储速度
- **启示**：我们这个项目也该尽早搭一个 host 侧的 SLVideo mock + H264 样本喂入测试，能不开盒子就不开——每次真机验证都要走"推二进制 + 启进程 + 读日志"，能自动化就自动化

**5. API 加密/风控应对（两个项目共同的实战经验）**

网易云用 `weapi`/`eapi` 非公开加密接口，项目里 `weapi.c`/`eapi.c` 单独成模块且明确"接口变了会暂时不可用、不绕过 VIP/地区限制"。B 站同理（WBI 签名、风控），搬 wiliwili 的 `api/` 时要有"接口随时可能失效、错误信息要可操作地显示给用户"的心理准备，别假设 API 永远返回预期字段。

**6. 许可证提醒**

ClouDS Music 是 **MIT**，MELODY PSP 是 **GPL-3.0**（其 MV 软解依赖 WiliMini 也是 GPL-3.0）。抄代码时注意：MIT 可宽松复用（保留署名），GPL-3.0 的代码若直接 copy 进我们的工程，会要求我们的项目整体也用 GPL-3.0 并保持开源——wiliwili 本身是 GPL-3.0，所以若最终基于 wiliwili 代码，这一点倒是一致。
