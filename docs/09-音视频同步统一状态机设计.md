# 音视频同步统一状态机设计（D28）

> 原则：**删掉不必要的机制，但不能撤销已经拍板的行为契约。**
>
> 本文只定义 D28 首期的同步所有权、状态、准备条件、控制入口、日志和验收标准。任务状态写在 [00-当前状态与任务](00-当前状态与任务.md)，实施证据写在 [02-开发进度日志](02-开发进度日志.md)，构建与调试命令见 [04-构建与真机调试](04-构建与真机调试.md)。

## 0. 目标与边界

D28 不建设通用音视频时钟系统，而是把所有会改变播放时间线的操作收敛到同一套准备协议：

> compat 创建唯一的同步 epoch，SlPlayer 在该 epoch 内准备视频和音频；两侧准备条件满足后，才进入目标播放状态。

覆盖：冷播/历史续播、seek、pause/resume、清晰度切换、自动降级、watchdog replay、CDN failover、暂停期间主动 seek。

| 优先级 | 首期要求 |
|---|---|
| P0 可靠性 | 旧 PCM 不混入新时间线；旧操作完成不能覆盖新操作；恢复位置正确；控制操作不竞争。 |
| P1 同步 | 冷播、seek、暂停恢复、切清晰度和恢复后，音频从与当前画面匹配的位置开始。 |
| P2 漂移 | 只记录估算趋势，先做真机基线；有证据后再另立任务。 |

首期不做：

- PCM 动态重采样、自动 drift reanchor；
- PID/PLL 或其他通用时钟控制器；
- 完整媒体时钟/PTS 映射和真实上屏时间戳依赖；
- 新增同步线程、D28 专用 `vpu_state`、epoch 历史注册表、新 `SL_EVT_SYNC`；
- 全项目时间单位重构。FFmpeg 保留原生 PTS/time_base，AudioPipeline 保留 sample count/PCM bytes，VPU 队列保留 SDK 毫秒值。

D22 继续使用现有 heartbeat、backpressure、frameAge 和 watchdog 机制。

## 1. 所有权与 epoch

### 1.1 两层所有权

| 组件 | 唯一职责 |
|---|---|
| compat（`mpv_stub.c`） | 唯一创建/结束 epoch；只维护一个 `active_epoch`；记录最终目标；写 `SYNC_BEGIN/SYNC_TARGET/SYNC_END`；处理 watchdog 强杀后的终态；原子发送 meta + 命令。 |
| SlPlayer | 只维护当前 epoch 的 `phase/desired_state/ready_mask`；执行视频、音频准备；写 `SYNC_READY/SYNC_START/SYNC_DRIFT`。不创建、不结束 epoch。 |
| AudioPipeline | 执行音频 reset/seek、清理旧 PCM、重建 stream、按启动点提交或预缓冲 PCM，并报告当前 seek 序列的最终结果。 |
| D22/watchdog | 沿用现有健康检测、恢复和降级职责；首期不新增 `vpu_state`。 |

compat 的 `active_epoch` 至少保存：

```text
epoch_id
reason
generation
request_id
target_ms            // pause 初始为 pending，最终由 SYNC_TARGET 确定
target_resolved
desired_state
active
```

不保存历史 epoch。新 epoch 开始前，compat 先把旧 active epoch 写为 `superseded`；watchdog 强杀 daemon 时写为 `error`；stop/EOF 写为 `ok`。

`epoch_id` 不等同于：

- `fileGeneration`：文件/流代次；
- `request_id`：单条控制命令身份；
- `AudioPipeline::seekSequence_`：音频线程内部 seek 序号。

### 1.2 Session meta 与 Sync meta 分离

现有 `sl_session_meta_t` 是 D27 会话身份，包含 `run/session/content/id/bv/cid/qn`，仍按 generation 保存，供统一日志和 watchdog 恢复使用。它不能被 D28 复用为“一次性命令上下文”。

新增独立的 `sl_sync_meta_t`：

```text
epoch=<n>
target_ms=<n|-1>
reason=<r>
desired=play|pause
```

两种数据共用 `SL_CMD_META` 帧，但生命周期不同：

| 数据 | 保存方式 | 生命周期 |
|---|---|---|
| Session Meta | 按 generation 保存 | 整个文件代次 |
| Sync Meta | 按 `(gen, req)` 暂存并一次性消费 | 仅对应的一条控制命令 |

daemon 收到 meta 后继续保存 session meta；D28 字段暂存为 pending sync context。只有紧接着收到 `(gen, req)` 完全匹配的命令时才消费该 context；不匹配则丢弃并记录协议错误。

meta 与对应命令必须在同一 `txMutex` 临界区连续发送。现有 `send_session_meta_and_open()` 只服务 open，需推广为通用 `send_meta_and_command()`：

1. 锁定 `daemonMutex`；
2. 分配 `request_id`；
3. 创建或替换 compat 的 active epoch；
4. 获取 session meta；
5. 锁定 `txMutex`；
6. 连续发送 meta 和 command。

普通 volume、heartbeat 等不改变时间线的命令不创建 epoch，也不需要 sync meta。新 epoch 的 desired state 必须显式传递；暂停期间切清晰度/自动降级不能擅自恢复播放。

## 2. 最小状态机

### 2.1 SlPlayer 本地状态

```cpp
enum class SyncPhase { IDLE, PREPARING, RUNNING, PAUSED };
enum class DesiredState { PLAY, PAUSE };

constexpr uint8_t VIDEO_READY = 1 << 0;
constexpr uint8_t AUDIO_READY = 1 << 1;

struct SyncState {
    uint64_t epoch_id = 0;
    int64_t target_ms = 0;
    SyncPhase phase = SyncPhase::IDLE;
    DesiredState desired = DesiredState::PLAY;
    uint8_t ready_mask = 0;
};
```

SlPlayer 只保存当前 epoch，不建历史列表。reason、generation、request_id 和音频序列号沿用 meta/既有字段，不复制进另一套状态系统。

| 状态 | 含义 |
|---|---|
| `IDLE` | 无有效播放同步生命周期。 |
| `PREPARING` | 当前 epoch 的视频/音频准备尚未全部完成。 |
| `RUNNING` | 当前 epoch 准备完成，PLAY 目标的音频启动计划已应用。 |
| `PAUSED` | 当前 epoch 已准备到暂停目标；旧 PCM 已清理，音频已定位，stream 有效，不提交可听 PCM。 |

不增加 `WAIT_FIRST_FRAME`、`WAIT_QUEUE_STABLE`、`WAIT_AUDIO_SEEK`、`SCHEDULED`、`CONVERGING` 等一级状态；它们是 PREPARING 内部条件或日志阶段。

### 2.2 Ready 屏障

`VIDEO_READY`：

- PLAY：当前 epoch 首帧成功提交，且现有视频队列稳定条件满足；
- PAUSE：旧视频队列已清理，demux 已定位到冻结位置，等待 resume 时继续读取。

`AUDIO_READY` 按 desired state 区分：

| 期望状态 | AUDIO_READY 的内部要求 |
|---|---|
| `PAUSE` | 当前音频 seek 成功；旧 SLAudio stream 已释放；新 stream 创建成功；通过 `SLAudio_GetQueuedAudioSamples()` 实际查询新 stream 队列为 0。不要求 preroll。 |
| `PLAY` | 上述条件已满足；当前 stream 仍有效；没有未完成或失败的旧 seek；软件 preroll 达到最低启动要求。 |

两个 bit 都满足后：

- `desired=PLAY`：写 `SYNC_READY`，调用 `scheduleStart()`，写 `SYNC_START`，进入 `RUNNING`；
- `desired=PAUSE`：写 `SYNC_READY`，进入 `PAUSED`，不写 `SYNC_START`。

## 3. Pause / Resume 的 epoch 边界

固定契约：**pause 创建 epoch；PAUSED 属于该 epoch；resume 不创建 epoch、不二次 seek 音频；暂停期间主动 seek 创建新 epoch。**

### 3.1 RUNNING -> PAUSED

1. compat 从当前有效播放状态创建 `reason=pause_resume` 的 epoch，初始 `target_ms=pending`，写 `SYNC_BEGIN desired=pause`。
2. compat 原子发送 meta + PAUSE，meta 的 desired 为 pause。
3. SlPlayer 在收到 PAUSE 命令时立即读取当前 `position_`，保存为该 epoch 的冻结目标。
4. SlPlayer 先调用 `AudioPipeline::requestSeek(frozen_target_ms)`：废弃旧启动点、旧压缩包和旧 PCM，进入静音并启动 reset/stream ACK。
5. 视频侧清空待呈现队列，并把共享 demux 定位到冻结目标；独立 DASH 音轨由 AudioPipeline 自己定位。
6. 共享 demux 在音频 reset 期间送达的音频包允许丢弃，因为 PAUSE 不要求 preroll。
7. `AUDIO_READY(PAUSE)` 与 `VIDEO_READY(PAUSE)` 满足后，SlPlayer 通过 `SL_EVT_PAUSED` 返回冻结位置；compat 检查 `(gen, req, epoch)` 仍有效，写入最终 `target_ms` 和 `SYNC_TARGET`，随后写 `SYNC_READY desired=pause`，进入 `PAUSED`。compat 保持该 epoch active，不写 `SYNC_END`。

Pause 的目标不能用 compat 缓存的 `resumePosition`，因为 progress 事件约 250ms 节流，heartbeat 约 500ms 轮询，均不是 pause 命令到达时的即时采样。SlPlayer 的 `position_` 是当前 SDK 条件下可用的最佳估算。

### 3.2 PAUSED -> RUNNING

resume 沿用 active epoch 和已经确定的 `target_ms`，只分配新的 `request_id`，原子发送同 epoch meta + RESUME。

SlPlayer 切回 `PREPARING/PLAY`，保留 AUDIO_READY 的 reset/stream 成功状态，只清除 PLAY 所需的 preroll 检查：

1. 不调用 `AudioPipeline::requestSeek()`；
2. 不重新 seek 共享 `AVFormatContext`；
3. 恢复视频流/首帧提交，从 pause 时已定位的 demux 位置继续读取；
4. AudioPipeline 允许解码，但 `audibleOutputAllowed=false`，`startAt_` 仍为 0，PCM 只进入 `preroll_`；
5. 软件 preroll 达到启动要求且 VIDEO_READY 满足后，统一 `scheduleStart()`；
6. 写 `SYNC_READY desired=play` 和 `SYNC_START`，进入 RUNNING。

当前 `paused_` 同时控制“是否读取/解码”和“是否允许可听输出”，必须拆成：

- `decodeAllowed`：是否继续 demux/decode；
- `audibleOutputAllowed`：是否允许向 SLAudio 提交可听 PCM。

这不是新的状态机，而是 AudioPipeline 内部两个互斥职责的明确化。

### 3.3 暂停期间 seek 与幂等

暂停期间用户主动 seek：compat 结束 pause epoch 为 `superseded`，创建新的 `reason=seek` epoch，目标为用户指定位置，`desired=PAUSE`；音视频都重新定位并完成准备，进入 PAUSED；之后 resume 沿用这个新 epoch。

重复 pause（已经 PAUSED）按幂等命令处理，不创建新 epoch。非 PAUSED 状态收到 resume 不创建 epoch。pause/resume 未完成时收到新的 seek/open/清晰度切换，以 compat 接受的新操作创建新 epoch，旧操作立即失效。

## 4. AudioPipeline 修正与 ACK 契约

### 4.1 必修问题

当前代码存在可验证缺口：

- `seekInternal()` 忽略 `ensureStream()` 返回值；
- `finishSeek()` 失败时仍可能清除 `seekActive_` 和 `seekMuted_`；
- `seekPending()` 只看 `seekRequest_`，请求被线程取走后可能仍在执行；
- `requestSeek()` 返回 void，调用方无法知道当前序列结果；
- `lastQueued_ = 0` 是软件缓存清零，不是硬件队列清空证据。

### 4.2 接口契约

| 接口 | 必须满足的行为 |
|---|---|
| `requestSeek(target)` | 返回本次递增的 `seekSequence`。 |
| `seekPending()` | 返回 `seekRequest_ || seekActive_`。 |
| `seekResult(seq)` | 返回当前最新序列的 pending / success / failed / stale。 |
| `prerollMs()` | 返回实际积累的 PCM 软件缓冲时长。 |
| `sinkQueueSamples()` | 返回最近一次由 `SLAudio_GetQueuedAudioSamples()` 实际查询的值。 |

`seekResult(seq)` 不建立历史序列注册表。旧序列被新请求覆盖后本来就不能成为当前准备条件。

`seekInternal()` 的成功结果必须同时满足：

1. self-demux 模式下 `av_seek_frame()` 成功；shared-demux 模式的定位由视频侧完成；
2. decoder 和 resampler 旧状态已处理；
3. 旧 SLAudio stream 已释放；
4. 新 SLAudio stream 创建成功；
5. 对新 stream 调用 `SLAudio_GetQueuedAudioSamples()`，确认实际队列为空。

失败时：`seekResult(seq)` 返回 failed，保持 mute，不置 AUDIO_READY，不得启动旧 PCM。

`finishSeek()` 只确认 reset/seek/stream/queue 阶段，不等于 PLAY 所需的完整 AUDIO_READY；SlPlayer 还要检查 preroll。

## 5. 视频/音频定位拆分

当前 `doSeek()` 同时做视频 seek 和 `audio_.requestSeek()`；resume 不能再走这个耦合路径。拆成两个可组合动作：

```text
doVideoPrepare(target, rebuildVideo)
doAudioPrepare(target)
```

| 操作 | 视频 | 音频 |
|---|---|---|
| OPEN | 定位、初始化 VPU stream | 初始化音频 pipeline |
| SEEK | demux seek、必要时重建 VPU | `requestSeek(target)` |
| PAUSE | 以冻结目标定位 demux，清空视频队列 | `requestSeek(target)`，清理旧 PCM 和硬件队列 |
| RESUME | 从 pause 已定位位置继续，准备首帧 | 不 seek；解除解码暂停，只积累 preroll |
| 清晰度/降级 | 新流定位至目标 | 新流音频定位至目标 |
| watchdog replay | 新 daemon 定位 | 新 daemon 初始化并定位 |

共享 demux 时，只有视频侧可以 seek 共享 `AVFormatContext`；AudioPipeline 的 `seekInternal()` 仅在 self-demux 模式下自己 seek。PAUSE 的顺序是：先让音频进入静音并 reset，再由视频侧定位共享 demux。resume 不重复定位，直接从已定位位置继续读取。

## 6. target_ms 与现有 bug

### 6.1 精度边界

`target_ms` 是 compat/SlPlayer 控制边界的唯一权威目标，整数毫秒。FFmpeg、AudioPipeline 和 VPU 队列保留各自内部表示。

必须打通：

```text
后端亚秒播放位置
 -> Activity/清晰度切换/自动降级使用控制位置
 -> VideoView extra 或 sync meta 保留三位小数秒/target_ms
 -> compat 归一化为唯一 target_ms
 -> SL_CMD_META(epoch, target_ms, reason, desired)
 -> daemon/SlPlayer
```

UI 展示进度可以继续是整数秒或百分比。`MPVCore::playback_time` 的 double 值用于保存控制精度，`video_progress` 的整数秒只用于显示、历史记录和 UI slider。异步请求视频链接期间不得重新读取展示进度作为控制目标。

旧 `start/end/seek seconds` 可保留给旧 daemon，但新 daemon 必须优先使用同一命令 meta 的 `target_ms`。不能让 open.start 和 meta.target_ms 成为两个权威。

pause 是唯一允许 `target_ms=pending` 的操作，因为 compat 创建 epoch 时 SlPlayer 尚未采样位置。最终位置必须通过 `SL_EVT_PAUSED` 返回并由 compat 写 `SYNC_TARGET`。

### 6.2 两个现有 bug

- CDN failover 不能从备用源原始 `open.start` 取恢复点；使用故障时 compat 最新有效位置，转成新 epoch 的 `target_ms`，旧 epoch 写 `superseded`。
- open 已带目标时，`VideoView` 不得在 `MPV_LOADED` 后再次执行等价历史 seek。保留 compat 去重作为旧 UI 防回归兜底。若 open 没有历史目标，仍必须保留一次真正的历史定位。

若视频与独立 DASH 音轨的 PTS 起点不一致，应先查清节目时间轴映射，不能用固定经验 offset 掩盖。

## 7. 起播、漂移与日志

### 7.1 起播

沿用现有策略：VIDEO_READY + AUDIO_READY 后，用估算画面位置与 `target_ms` 计算 `skip_ms`；preroll 足够才调用 `scheduleStart()`。画面未到目标继续静音等待；已越过目标则从 preroll 跳过对应内容。禁止正常路径使用固定 `offset_ms`。`SL_SYNC_AUDIO_OFFSET_MS` 仅作诊断，正式验收设为 0。

`presentation_ms = maxSubmittedFramePts - videoQueueMs` 只是估算，不是真实上屏时间戳。音频 PCM 提交量减硬件队列也只是消费进度估算。

### 7.2 RUNNING 只观测

RUNNING 首期只记录约 1s/5s/10s 和必要的低频 drift estimate，不自动补偿、不自动 reanchor。P3 的 `vpu_state` 标为延期；首期使用 D22 现有 heartbeat 字段。

### 7.3 日志职责

| 日志 | 写入方 | 语义 |
|---|---|---|
| `SYNC_BEGIN` | compat | 创建 epoch，记录目标或 `pending`。 |
| `SYNC_TARGET` | compat | pause 等延迟采集目标最终确定。 |
| `SYNC_READY` | SlPlayer | 当前 desired state 的准备屏障完成；pause 和 resume 可在同 epoch 各出现一次。 |
| `SYNC_START` | SlPlayer | PLAY 目标已应用音频启动计划，不代表真实上屏/出声。 |
| `SYNC_DRIFT` | SlPlayer | 运行中估算样本，只观测。 |
| `SYNC_END` | compat | epoch 真正结束：stop/EOF、被替代或失败。 |

日志示例：

```text
SYNC_BEGIN  epoch=<n> target_ms=<n|pending> reason=<r> desired=<play|pause>
SYNC_TARGET epoch=<n> target_ms=<n> source=slplayer_position
SYNC_READY  epoch=<n> desired=<play|pause> ready_mask=<bits> video=<summary> audio=<summary>
SYNC_START  epoch=<n> target_ms=<n> presentation_estimate_ms=<n> skip_ms=<n> preroll_ms=<n>
SYNC_DRIFT  epoch=<n> elapsed_ms=<n> drift_estimate_ms=<n> video_queue_ms=<n> audio_queue_samples=<n>
SYNC_END    epoch=<n> status=<ok|superseded|error> reason=<stop|eof|new_epoch|watchdog|seek_failed|...>
```

每条 `SYNC_*` 必须带 D27 的 `run/session/gen/req` 前缀，正文带 `epoch`。compat 的 BEGIN/TARGET/END 使用 active epoch 保存的创建身份；SlPlayer 阶段日志使用触发该阶段的当前 req。异步日志必须捕获当前日志上下文副本，不能依赖之后可能被新命令覆盖的全局上下文。不新增 `SL_EVT_SYNC`。

## 8. 实施顺序

| 步骤 | 内容 | 完成标准 |
|---|---|---|
| S01 meta/epoch 协议 | session meta 与 sync meta 分离；`send_meta_and_command()`；daemon 按 `(gen, req)` 一次性消费 sync meta；compat active epoch 与 BEGIN/END。 | meta 与命令不能被其他命令插入；不匹配 meta 不污染后续命令；watchdog kill 后 compat 写 error。 |
| S02 Audio ACK | 检查 `ensureStream()`；失败保持静音；`requestSeek()` 返回 seq；`seekPending()` 覆盖 request+active；实现 `seekResult/prerollMs/sinkQueueSamples`。 | seek/CreateStream 失败不解除 mute、不置 AUDIO_READY；SDK queue 使用实际查询。 |
| S03 最小状态与准备拆分 | SlPlayer 四状态和 ready mask；拆出 `doVideoPrepare()`/`doAudioPrepare()`；PAUSE 不要求 preroll，PLAY 要求 preroll。 | 同一时刻一个 active epoch；pause/resume 准备条件按 desired 区分。 |
| S04 pause/resume 契约 | pause 目标延迟采集；SL_EVT_PAUSED 返回位置；resume 同 epoch 不二次 audio seek；decodeAllowed 与 audibleOutputAllowed 分离。 | pause epoch 最终 target 可追溯；resume 的 audio seekSequence 不增加。 |
| S05 精度与入口 | 修复 UI 整数秒目标；extra/meta 保留亚秒；daemon 优先 meta target_ms；修 MPV_LOADED 等价 seek；failover 使用故障时位置。 | 切清晰度/降级保留亚秒；续播只有一次实际定位；failover 不回跳。 |
| S06 真机验收 | 跑启动、seek、pause/resume、暂停中 seek、切清晰度、降级、replay、failover、无音频。 | P0/P1 通过；只记录 drift，不启用补偿。 |

## 9. 真机验收

普通稳定负载和接近设备能力上限的高负载都要覆盖；关键场景重复测试，连续播放观察不少于 60 秒。正式验收 `SL_SYNC_AUDIO_OFFSET_MS=0`。

| 场景 | 验收重点 |
|---|---|
| 冷播/历史续播 | 准备完成后才启动；目标保留亚秒；没有等价二次 seek。 |
| 连续 seek | 最新 epoch 生效；旧序列不能解除新 seek 静音。 |
| pause/resume | pause 新 epoch、旧硬件队列清空且 stream 重建；resume 同 epoch、不二次 audio seek、preroll 满足后启动。 |
| 暂停中 seek | 新 seek epoch、desired=PAUSE；之后 resume 沿用该 epoch。 |
| 清晰度/自动降级 | 使用最新亚秒位置，不回跳、不继承旧启动计划；暂停时切换仍保持暂停。 |
| watchdog replay | 旧 epoch 由 compat 写 error；新 daemon 用新 epoch 和恢复位置。 |
| CDN failover | 新 epoch 使用故障时位置，不使用原始 open.start。 |
| 无音频/seek 失败 | silent 路径不阻塞；失败不置 AUDIO_READY、不错误放声。 |

通过标准：compat 同一时刻只有一个 active epoch；meta/命令正确配对；P0/P1 场景无旧 PCM 重播、旧位置回跳和命令互相覆盖；视听结果经真实素材/采集确认。

## 10. 延期与兼容

| 项目 | 状态 |
|---|---|
| `vpu_state` 新枚举/heartbeat | P3 延期；只有未来闭环需要且 D22 现有字段不足时再做。 |
| PCM 补偿、自动 reanchor | 延期；真机基线证明持续漂移后另立设计。 |
| 完整媒体时钟/PTS 映射、真实上屏时间戳 | 延期；需有 SDK 能力和明确收益。 |
| `SL_EVT_SYNC` | 取消；复用现有命令/meta 和日志。 |
| epoch 历史注册表 | 取消；首期只维护一个 active epoch。 |

渐进兼容：

- 新 compat + 新 daemon：执行完整 D28 契约；
- 新 compat + 旧 daemon：旧 daemon 忽略未知 sync 字段，compat 由 `target_ms` 生成三位小数秒旧参数；只验旧路径不回归；
- 旧 compat + 新 daemon：缺少 epoch/sync 字段时走旧 D27 路径，不创建伪 D28 epoch、不强制 `SYNC_*`。

**D28 首期完成定义：compat 唯一管理同步 epoch；SlPlayer 用四态和两个 ready bit 完成音视频准备；pause/resume 遵循同一 epoch 和 P5 quiet 契约；目标位置保留亚秒精度；音频失败不会错误放声；所有入口不再各自维护启动策略。长期漂移只记录，不自动纠偏。**
