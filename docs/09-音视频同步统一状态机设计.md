# 音视频同步统一状态机设计（D28）

> 本文只定义同步架构、接口和验收契约。任务状态只写在 [00](00-当前状态与任务.md)，实施过程与真机证据只写在 [02](02-开发进度日志.md)，构建与调试命令见 [04](04-构建与真机调试.md)。

## 1. 目标与边界

### 1.1 目标

把首播、续播、快进快退、暂停恢复、清晰度切换、硬卡顿自动降级、watchdog replay、CDN 备用源切换等所有会中断音视频时间线的操作，收敛为同一个同步状态机。

每个入口只允许决定两件事：

1. 为什么重启同步：原因、内容、清晰度、generation、session。
2. 新时间线从哪里开始：精确的 `target_us`。

入口本身的网络请求、UI 跳转、VPU 重建、daemon 重启等耗时只用于诊断，不参与音频启动时刻的计算。

### 1.2 非目标

- 不改变 D21/D22 的 VPU 健康检测、硬卡顿自动降级范围或 Toast 文案。
- 不把同步失败静默降级为“先出声再纠偏”。
- 不依赖固定经验偏移作为正常播放策略。
- 不在本文规定真实上屏时间戳的 SDK 改造；状态机应允许以后替换时钟源而不改外层场景逻辑。
- 不恢复任何旧测试脚本作为同步验收依据。

## 2. 核心决策

| 编号 | 决策 |
|---|---|
| D28-1 | 每次时间线不连续都创建一个 `SyncEpoch`，epoch 是同步的唯一所有权单位。 |
| D28-2 | 全链路媒体时间统一为 `int64` 微秒；`target_us` 是唯一权威起点。旧秒字段只作为输入格式兼容，在 compat 边界立即转换为微秒。 |
| D28-3 | 所有重新起流必须经过同一个 `beginEpoch()`；任何场景都不允许自己计算音频偏移或直接调用音频启动。 |
| D28-4 | 起点在 `beginEpoch()` 时冻结；入口耗时只记录，不进入同步公式。 |
| D28-5 | 音频启动点只由媒体时间判断：视频首帧已提交、队列稳定、音频 seek 完成，且呈现位置到达目标。 |
| D28-6 | 墙钟只用于提交 PCM 的调度和存活超时，不能替代 `presentationMs` 判断画面位置。 |

| D28-8 | 同步失败必须显式失败或按既定健康流程处理，不能强行启动音频。 |
| D28-9 | 计划与真实代码冲突时先停止实施，由用户拍板后更新本文，不能先在代码里悄悄改口径。 |
| D28-10 | `firstFramePtsAfterSeekMs`、`seekDisplayTargetMs`、`measuredVideoLatencyMs` 一律降级为诊断字段，不参与同步求解。 |

## 3. 数据模型

### 3.1 Epoch 字段

| 字段 | 含义 |
|---|---|
| `epoch_id` | 单调递增的同步纪元 ID；新 open、seek、resume、replay、failover 都递增。 |
| `reason` | `open` / `history_resume` / `seek` / `pause_resume` / `quality_change` / `auto_downgrade` / `watchdog_replay` / `failover` / `next` / `live_connect` / `drift_reanchor`。 |
| `target_us` | 新时间线的权威媒体起点，由入口冻结。 |
| `target_source` | 目标来源和捕获时刻，例如 `pause_command`、`watchdog_progress`、`user_seek`。 |
| `content_key` / `session` / `generation` / `request_id` | 与 D27 统一日志一致的身份字段。 |
| `decision_wall_ms` | 决定重启的墙钟时间，仅诊断。 |
| `prepare_start_wall_ms` | 新流开始准备的墙钟时间，仅诊断。 |
| `first_frame_pts_us` | 新流首个成功提交帧的 PTS。 |
| `queue_stable_us` | 队列进入稳定状态的墙钟时间。 |
| `audio_seek_done_us` | 音频 seek 完成的墙钟时间。 |
| `audio_start_wall_ms` | 实际提交第一段可听 PCM 的墙钟时间。 |
| `audio_media_us` | 本次 epoch 已消费的音频媒体时间；不受重采样后的 sink PCM 时长变化影响。 |
| `queued_audio_media_us` | 已提交但尚未播放的 PCM 按当前补偿比例折算回的媒体时长。 |
| `skip_us` | 为使音频内容从 `target_us` 开始而跳过的预缓冲长度。 |
| `state` | 当前状态机状态。 |

诊断字段不进入同步公式：`first_frame_pts_us`、`seek_display_target_us`、`measured_video_latency_us`。它们只用于解释关键帧距离、入口准备时间和 VPU 队列状态；缺少真实上屏时间戳时，不能拿关键帧 PTS 推断实际呈现时刻。

### 3.2 时钟定义

- `presentation_us`：当前估算的画面呈现媒体时间。当前实现是 `maxSubmittedFramePtsUs - videoQueuedUs`，这不是 SDK 真实上屏时间戳，日志必须标为估算值。
- `audio_content_us`：估算的正在可听音频媒体时间。按 `target_us + skip_us + audio_media_us - queued_audio_media_us` 计算；无补偿时 `audio_media_us` 等于已提交 PCM 的媒体时长。不能只用 sink 已提交量。
- `wall_ms`：单调墙钟，只用于调度与超时，不用于判断是否到达目标媒体时间。

以后若 SDK 提供真实上屏帧时间戳，只替换 `presentation_us` 的来源；状态机和 `target_us` 契约不变。

### 3.3 时间字段单位契约

- 内部权威单位统一为 `int64` 微秒；所有新字段命名为 `*_us`。墙钟诊断字段仍可用 `wall_ms`，但不得与媒体时间混用。
- `target_us`、`start_us`、`end_us`、`position_us`、`skip_us`、`drift_us` 一律保存整数微秒。`open.start`、loadfile extra `start/end`、debug `target/delta` 等旧字段至少保留毫秒精度，compat 在边界把它们解析并归一化到 `target_us`；旧整秒只是允许的输入值，不是独立权威。
- 兼容字符串可以使用小数秒，但必须由同一个 `target_us` 生成，至少保留 3 位小数，建议 6 位；不得从一个目标生成秒值后再独立反推另一个目标。
- 新 IPC 以 `SL_CMD_META.target_us` 为准；`SL_CMD_OPEN` 可同时携带 `start_us/end_us` 和旧 `start/end`，旧字段只供旧 daemon 回退。D28 路径下 `SL_CMD_OPEN` 的旧秒字段即使存在，也不得覆盖 meta 的 `target_us`。
- UI 的播放进度、历史进度、debug 目标、watchdog 恢复位置、CDN failover 位置、自动降级位置都在 compat 边界转成 `target_us`。`wall_ms` 只记录入口耗时，禁止加到媒体目标上。

| 层 | D28 权威字段 | 兼容输入 |
|---|---|---|
| UI/Activity | `target_us`、`position_us` | 上游 API 的秒值 |
| loadfile extra | `start_us`、`end_us`、`meta.target_us` | 小数秒 `start/end` |
| compat | `epoch_id`、`target_us`、`sync_reason` | `open.start`、UI 秒值 |
| SlPlayer | `start_us`、`seek_target_us` | 仅在无 meta 的新字段时回退到旧秒值 |
| 日志 | `*_us` | 旧 `start=<秒>` 只作对照，不参与判断 |

## 4. 统一状态机

```text
IDLE
  | beginEpoch(reason, target_us, identity)
  v
PREPARING
  | 旧 epoch 作废；音频静音；目标冻结；视频/音频分别定位和重建
  v
WAIT_FIRST_FRAME
  | 首个视频帧成功 SubmitFrame
  v
WAIT_QUEUE_STABLE
  | 视频队列连续稳定 && 音频 seek 完成
  v
WAIT_TARGET_POSITION
  | presentation_us >= target_us
  v
SCHEDULED
  | scheduleStart 已下发，等待音频线程真正提交第一段可听 PCM
  v
RUNNING
  | 周期性采样并进入 RUNNING 内部控制回路
  v
END / SUPERSEDED / FAILED
```

`RUNNING` 内部闭环：

```text
CONVERGING
  | 连续有效样本落在死区
  v
CONVERGED
  | 连续同向样本超过微纠偏阈值，且 vpu_state=STABLE
  v
CORRECTING
  | 补偿后进入死区 -> CONVERGED；不收敛 -> REANCHOR 或 FAILED

VPU 进入 PRESSURE/STALL -> SUSPENDED_VPU，禁止纠偏并交给 D22/watchdog
```

### 4.1 状态动作

| 状态 | 进入动作 | 离开条件 |
|---|---|---|
| `PREPARING` | 递增 epoch；旧 epoch 事件全部丢弃；音频静音；冻结 `target_us`；视频/音频 seek 并行准备 | 首个视频帧成功提交 |
| `WAIT_FIRST_FRAME` | 记录 `first_frame_pts_us`；watchdog 继续挂起 | 首个视频帧成功提交 |
| `WAIT_QUEUE_STABLE` | 记录 `queue_stable_us`、`audio_seek_done_us`；计算 `skip_us` | 队列稳定且音频 seek 完成；无音频时直接进入 `SCHEDULED` |
| `WAIT_TARGET_POSITION` | 如果画面已越过目标，计算越过量并作为 `skip_us`；未越过时等待 | 调用统一的 `scheduleStart` |
| `SCHEDULED` | 等待音频线程应用启动点 | 第一段可听 PCM 提交 |
| `RUNNING` | 周期性记录 `presentation_us - audio_content_us` | 新 epoch、正常结束、错误 |

`RUNNING` 内部子状态不因为原因不同而改变判据；`reason` 只决定起点来源和准备方式。

起播等待失败只看媒体位置推进：呈现位置高水位在 `SL_SYNC_NO_PROGRESS_MS` 内不推进时进入 `FAILED`。`RUNNING` 内的纠偏失败另按第 6.4 节判断，不复用这个条件。入口等待多久不算失败。

无音频流时 `audioQuiet` 恒为 1，`SYNC_START` 写 `audio_mode=silent` 后进入 `RUNNING`；直播跳过 `WAIT_TARGET_POSITION`，`target_us=0` 表示流起点，仍按队列稳定后的 `presentation_us` 计算 `skip_us`。

## 5. 统一起点安排

这是本设计的核心：**每次重新播放都必须有同一个起点协议，而不是把入口延迟带进同步公式。**

### 5.1 `beginEpoch()` 契约

唯一权威入口在 compat：

```text
beginEpoch(reason, target_us, content_key, session, generation, request_id, flags)
```

它必须完成：

1. 由 compat 创建并递增 `epoch_id`；该 epoch 是跨进程、跨 watchdog 重启的唯一权威对象，SlPlayer 收到的必须是已创建的 epoch。
2. 由 compat 冻结 `target_us`，后续任何进度上报都不能改写当前 epoch 的目标。
3. 让旧 epoch 失效，丢弃旧 seek 完成、旧音频启动点和旧 watchdog replay。
4. 立即阻断旧音频继续出声；新音频在 `SYNC_START` 前不得提交可听 PCM。
5. 视频和音频都定位到同一个 `target_us`；VPU 重建最多一次。
6. 不允许 `loadfile` 之后再隐式插入一次“续播 seek”。若目标在 loadfile 前不可知，必须推迟 loadfile 或先停在 `PREPARING`。
7. 由 compat 写一条 `SYNC_BEGIN`，记录入口耗时但不把它们用于计算。

冻结目标不等于等待期间让旧流继续定义播放位置：

- `beginEpoch()` 一旦成功，旧流的 `playback-time`、音频提交和进度事件都不再是当前时间线；UI 显示与 health 判据一起进入 transition。
- 暂停命令被接受时立即冻结 `target_us`；旧音频必须在 `SYNC_START` 前达到 `audioQuiet`。具体采用 `requestSeek(target_us)`、释放/重建 stream 还是自然排空，按 D28-P5 拍板；仅调用 `setPaused(true)` 不足，因为已提交的音频仍可能继续播放约一个队列深度。
- `WAIT_QUEUE_STABLE` 的 `audio_quiet` 门禁要求旧音频队列已清空、新音频尚未提交可听 PCM；resume 只复用暂停时冻结的 `target_us`，不重新读取 UI 整数进度。
- 旧流可以继续解码或做资源回收以缩短切换时间，但它只能维持最后一帧可见，不能继续推进 `target_us`。
- 新流真正 open 后只从已冻结的 `target_us` 恢复。入口耗时不会被加到目标上，否则不同入口延迟会直接变成不同的续播位置误差。
- `decision_wall_ms` 与 `prepare_start_wall_ms` 的差值用于诊断入口成本；它们与 `target_us` 必须分开记录，禁止混用。

### 5.2 入口到目标的映射

| 场景 | 权威 `target_us` 来源 | 起点要求 |
|---|---|---|
| 冷播无历史 | `0` | 新 open，创建 epoch。 |
| 历史续播 | 历史接口返回的位置归一化为 `target_us` | 只在 loadfile 的 meta 中传一次；取消 `MPV_LOADED` 后的二次 seek。 |
| 快进/快退 | 用户请求归一化为 `target_us` 或 `delta_us` | 相对量在 compat 边界换算成绝对微秒；方向不进入同步公式。 |
| 暂停恢复 | 暂停命令被接受时冻结的呈现位置 | resume 不重新从 UI 整数进度取值；复用暂停时冻结值。 |
| 手动切清晰度 | 切换命令被接受时的精确呈现位置 | 新 loadfile 带 `target_us`；不经过整秒截断。 |
| 自动降级 | hard 判定时 compat 的最新精确进度 | 与 watchdog replay 共用同一入口；新 qn 流从该点继续。 |
| watchdog replay | compat 的 `resumePosition` | 新 daemon 后作为新 epoch；旧 session meta 复用但 epoch 更新。 |
| CDN failover | 错误发生时的当前精确呈现位置，归一化到 `target_us` | 不能沿用原始 open 的 `start`。 |
| RUNNING 纠偏失败 | 当前 `presentation_us` | `reason=drift_reanchor`；只创建新 epoch，不重建内容或切换清晰度。 |
| EOF 自动续播 | `0` | 新内容、新 session、新 epoch。 |
| 直播重连 | `0`（流起点） | 创建 epoch，但不进入 `WAIT_TARGET_POSITION`；按队列稳定后的呈现位置计算 `skip_us`。 |

### 5.3 入口延迟的处理

- 入口耗时包括：API 请求、UI 页面切换、Range 建连、daemon fork、VPU Free/Create、音频 stream 重建。
- 这些值写入 `SYNC_BEGIN` / `SYNC_PREPARED` 的 `wall_*` 字段，便于比较入口成本。
- 音频启动公式只读取 `target_us`、`presentation_us`、队列稳定状态和音频预缓冲长度。
- 因此快进和快退、首播和降级可以用同一个求解器；差异只体现在入口准备时间，不体现在音频偏移。

## 6. 统一求解器

### 6.1 输入

- `target_us`
- `presentation_us`
- `video_queue_us`
- `audio_preroll_us`
- `audio_queue_us`
- `audio_seek_done`

明确排除：`first_frame_pts_us`、`seek_display_target_us`、`measured_video_latency_us` 只写日志，不参与第 6.2 节的任何计算。

### 6.2 规则

1. 只有 `videoStarted && queueStable && audioSeekDone && audioQuiet` 后才允许求解；`audioQuiet` 表示旧 epoch 的已提交 PCM 已清除，且新 epoch 尚未提交可听 PCM。
2. 若 `presentation_us >= target_us`，设置 `skip_us = presentation_us - target_us`，限定不超过可用音频预缓冲长度。
3. 若 `presentation_us < target_us`，保持音频静音，等待画面位置到达目标；到达后按越过量设置 `skip_us`。
4. `scheduleStart()` 只应用本次 epoch 的 `skip_us` 和绝对墙钟启动点；旧 epoch 的调用无效。
5. 正常路径不允许额外 `offset_us`；诊断参数单独记录，默认 0。

### 6.3 起播后观察

进入 `RUNNING` 后记录 1 秒、5 秒和 10 秒的：

```text
drift_us = presentation_us - audio_content_us
```

基线阶段只记录趋势，不做自动纠偏。闭环控制按第 6.4 节实施；是否进入 `CORRECTING` 必须由第 10.1 节的阈值原子步骤和真机矩阵决定。

这里的 `drift_us` 已扣除未播放音频队列，但 `presentation_us` 仍是估算值；它只能比较趋势，不能当作真实音画偏差。第 6.4 节的 `E_sync` 是经过门禁、滤波和阈值判断后的代理反馈，不是单点直接使用。

### 6.4 RUNNING 闭环控制契约

误差与采样：

- `E_sync = median(presentation_us - audio_content_us)`，取连续 `N` 个 500ms 样本的中位数，避免单点队列抖动触发纠偏。
- 有效样本必须满足：`vpu_state=STABLE`、非 transition、`video_queue_us` 稳定、视频帧仍在提交、音频已启动且音频队列稳定。
- `vpu_state=PRESSURE` 时只记录，不纠偏；`STALL` 时交由 D22/watchdog，D28 进入 `SUSPENDED_VPU`。

决策分三档：

1. `|E_sync| <= D_dead`：进入 `CONVERGED`，不调整。
2. `D_dead < |E_sync| <= D_micro` 且方向连续：进入 `CORRECTING`，在 `AudioPipeline` 中做有上限的 PCM 重采样补偿；不得用墙钟跳变或全局 offset。
3. `|E_sync| > D_reanchor` 或纠偏后不收敛：以当前 `presentation_us` 为 `target_us` 创建新 epoch，写 `reason=drift_reanchor`；单位时间内重新 anchor 次数受限。

控制约束：

- 一次只允许一种执行器生效：PCM 重采样或重新 anchor，不能同时执行。
- 纠偏必须记录调整前/后的 `E_sync`、补偿量、状态变化和执行原因。
- 死区、微纠偏上限、重 anchor 阈值、采样数、最大补偿速率先通过 env 配置并由第 10 节矩阵标定；未标定前自动纠偏默认关闭。
- 稳定后保留滞回窗口，避免在阈值附近来回切换；连续失败写 `SYNC_END status=error`，不允许强行继续播放不同步的流。

## 7. 接口改动范围

### 7.1 UI / compat

- UI 的 `setProgress/getProgress`、`VideoView::setUrl`、`genExtraUrlParam` 增加整数微秒接口；上游秒值只在边界接受，不进入 D28 同步计算。
- `updateVideoLink()` 使用当前 `position_us`，而不是 `MPVCore::video_progress` 整数秒。
- compat 把所有入口目标归一化为 `target_us`，写进 `SL_CMD_META`；D28 路径不依赖 `open.start` 秒值。
- compat 是所有 restart 的唯一权威 `beginEpoch()` 调用方；epoch 创建后再发 `open` / `seek`。
- `MPV_LOADED` 后与 loadfile `start` 等价的 seek 必须去重或取消。

### 7.2 IPC

- `SL_CMD_META` 承载 `epoch`、`target_us`、`sync_reason`；不新增 `beginEpoch` IPC。
- `SL_EVT_SYNC` 统一上报 epoch 状态变化；字段见第 8 节。
- `SL_CMD_OPEN` 保留旧 `start/end` 兼容字段，并新增 `start_us/end_us`；D28 路径以 meta 的 `target_us` 为唯一权威，旧秒字段不得覆盖它。
- `SL_CMD_SEEK` 增加 `target_us`；旧秒级 seek 只在无新字段时回退。
- heartbeat 继续提供 `bp/vq/pos`，供 D22 与同步共同判断队列是否停滞。

### 7.3 SlPlayer / AudioPipeline

- `SourceSpec.startSeconds` 改为 `start_us/end_us`，只在 FFmpeg seek 的 `av_rescale_q()` 边界转换为 FFmpeg timestamp；不得在 IPC、状态机或日志中退化回秒。
- `SlPlayer` 只持有当前 daemon 进程内的本地状态机，执行 compat 已创建的 epoch 并上报阶段；它不创建、不递增、不关闭 epoch，也不写 `SYNC_END`。watchdog 强杀后，原 epoch 的 `error/superseded` 一律由 compat 写。`doSeek()`、`pauseFlush()`、pause resume 只向状态机提交目标，不直接调用音频启动。
- `AudioPipeline` 只提供 `requestSeek()`、预缓冲长度、启动点应用和已提交/排队量查询，不感知“快进”“降级”等业务原因。
- `firstFramePtsAfterSeekMs`、`seekDisplayTargetMs`、`measuredVideoLatencyMs` 只保留为诊断字段，统一改名或映射到 `first_frame_pts_us`、`seek_display_target_us`、`measured_video_latency_us` 日志；不得参与求解，也不得作为第二套偏移来源。

## 8. 日志与检查契约

统一前缀沿用 D27：`[HH:MM:SS.mmm][SOURCE][run][session][gen][req]`。

新增事件：

```text
SYNC_BEGIN      epoch=<n> reason=<r> target_us=<n> source=<s> qn=<n> wall=<ms>
SYNC_PREPARED   epoch=<n> first_pts_us=<n> queue_us=<n> audio_seek_us=<n> audio_quiet=<0|1>
SYNC_START      epoch=<n> skip_us=<n> present_us=<n> audio_queue_us=<n> audio_media_us=<n> audio_mode=<audible|silent> wall=<ms>
SYNC_DRIFT      epoch=<n> elapsed_s=<n> present_us=<n> audio_content_us=<n> drift_us=<n> qn=<n> frame_age=<ms> vq=<ms> bp=<0|1> submitted_us=<n>
SYNC_END        epoch=<n> status=ok|error|superseded reason=<r>
```

`check-debug-run.sh` 的结构检查：

- 每个 epoch 恰好一个 `SYNC_BEGIN` 和一个 `SYNC_END`；reanchor 生成新 epoch，不复用旧 epoch 的终态。
- `SYNC_START` 必须晚于 `SYNC_PREPARED`，且同一 epoch 只能出现一次。
- `SYNC_PREPARED` 的 `audio_quiet` 必须为 1；pause/resume run 还要确认旧音频队列没有残留 PCM。
- 同一 epoch 的 `target_us` 在 CMD / meta / PLAYER / AUDIO 日志中一致。
- 若日志同时出现旧 `start=<秒>`，必须能由同一 `target_us` 转换得到；检查脚本不得用旧秒值覆盖或重新推导目标。
- 自动降级的 `target_us` 必须来自精确进度，不得等于被截断的整秒值。
- 验收 run 的 manifest `sync_offset_ms` 必须为 0。
- 旧 `start=<整数秒>` 若与新 `target_us` 并存，检查脚本以 `target_us` 为准但记录差异。

## 9. 失败与竞态

- 新 epoch 到达后，旧 epoch 的 seek 完成、audio start、watchdog replay 全部失效；epoch 的创建和终态写入只发生在 compat。
- watchdog 强杀和自动降级同时发生时，compat 只保留一个赢家；另一个由 compat 写 `superseded`，不能两个都 open。
- 音频不可用时使用静音播放，但 epoch 仍走完整生命周期，避免状态机停滞。
- 同步等待失败写 `SYNC_END status=error` 并按现有错误流程结束；是否转成自动降级属于后续决策，不在本状态机内隐式发生。
- 直播没有 seek 语义时跳过 `WAIT_TARGET_POSITION`，但仍记录 epoch 和首帧/音频启动。

### 10.3 验收

- 所有 run 的 `check-debug-run.sh` 通过新的结构检查。

### 12.2 各场景问题是否由同一状态机解决

| 场景 | 图中问题 | D28 处理方式 | 结论 |
|---|---|---|---|
| 首播，无 `start=` | 一次性自动测，且没有稳态闭环 | `target_us=0`；所有入口走 `PREPARING → WAIT_FIRST_FRAME → WAIT_QUEUE_STABLE → WAIT_TARGET_POSITION → RUNNING`，`RUNNING` 内按第 6.4 节闭环 | 起播策略和纠偏策略已统一；纠偏代码尚未实施 |
| 续播/历史记录 | 策略与 seek 共用内核，问题在 `start=` 精度 | `target_us` 为唯一权威起点，loadfile 前冻结；取消 `MPV_LOADED` 后二次 seek | 状态机解决策略，微秒字段解决精度 |
| 快进/快退 | 看起来有两套算法，差异来自关键帧距离和重建耗时 | 方向只影响 `target_us` 来源；准备耗时只写 wall 字段，不进入求解 | 同一状态机；不承诺消除入口耗时差异 |
| 暂停/恢复 | 旧音频队列仍可能播放；恢复等价于另一次续播 | 暂停命令冻结目标并静默旧音频；`audioQuiet` 是 `PREPARED` 门禁；resume 复用目标 | 设计已覆盖，实施时必须验证队列确实清空 |
| 清晰度切换 | 当前位置被截成整秒 | 切换命令时取精确呈现位置，构造 `target_us`；新 loadfile 带微秒目标 | 状态机与字段共同解决 |
| 硬卡顿自动降级 | watchdog 精确位置与续播整秒起点不一致 | hard 判定时冻结 compat 精确进度；复用 watchdog replay 的同一 `beginEpoch()` | 状态机与字段共同解决；自动降级逻辑仍属 D22 |
| watchdog replay | 单独 open 路径，可能形成第二套策略 | replay 只是 `reason=watchdog_replay` 的 epoch；目标来源和状态机不变 | 同一状态机 |
