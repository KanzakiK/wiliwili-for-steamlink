# 架构与关键决策

> 已拍板的内容，后续会话不要重新论证。详细背景见归档文档第四、六章。

## 一、总决策

| 项 | 决策 | 理由 |
|---|---|---|
| 做什么 | Steam Link 原生 B 站客户端，自写/移植 | 没有现成客户端；Kodi/Moonlight 已证明可行 |
| UI | **移植 wiliwili**（borealis + nanovg，GLES2 + SDL2） | 不手写 UI；PSV 版官方支持 GLES2 |
| 播放 | **SLVideo 硬解 + FFmpeg 解封装 + SLAudio** | 不用 mpv；单核 + 263MB 内存 |
| mpv | **不引入**；用 MPV 桩让 wiliwili UI 编译 | 体积/GLES2/性能都不合适 |
| 许可证 | 项目整体 GPL-3.0 | wiliwili/ThirdBili/MELODY 都是 GPL |
| Moonlight | 停在官方 6.2.0，V+ 不再修 | 与项目无关，已结案 |

## 二、Steam Link 硬件与底座

- SoC：Marvell DE3005（ARMADA 1500 Mini），**单核 1GHz ARMv7**，NEON，hard-float
- GPU：Vivante GC1000，**仅 GLES2**
- 内存：512MB DDR3，Linux 可见 263MB，开机后可用约 140～160MB
- 系统：Linux 3.8 / glibc 2.19 / Qt 5.14.1 / **SDL2（wiliwili UI 用）/ SDL3（SLVideo 依赖，`libSDL3.so.0.5.0`）**
- 固件自带：`libSLVideo.so.1`、`libSLAudio.so.1`、libcurl 7.26、OpenSSL 1.0.1c、freetype/png/jpeg/zlib
- 没有：mpv、FFmpeg（需自编并打包）

## 三、SLVideo 约束（逐条对过头文件）

| 约束 | 影响 |
|---|---|
| 只支持 `k_ESLVideoFormatH264` | B 站必须选 AVC 流 |
| `bLowLatency=0` 才支持 B 帧 | 点播用 0 |
| 码率上限约 30Mbit/s | 高码率 1080P 要压 |
| 没有 seek 接口 | seek = `FreeStream` 重建 + 关键帧重喂 |
| **stream 没有目标区域接口** | `SetOverlayDisplayArea` 只对 ARGB overlay 有效；硬解视频只能全屏输出，播放页必须全屏 |
| `BeginFrame/WriteFrameData/SubmitFrame` 返回 int | 失败要处理；BeginFrame 失败是背压信号 |
| `GetQueuedVideoMS` = 已提交未上屏的 ms | **480p 稳态约 2.1s、360p 约 2.7s，是固有水位，不是积压**；不能拿 300ms 当缓冲目标 |
| overlay 同时只能显示 1 个 | 多 overlay 只能轮流 show |
| **overlay 与 GUI 窗口抢同一个硬件平面** | `CreateOverlay` 会改变平面尺寸；Moonlight 用“建满屏 overlay→Show→Hide→Free”刷回全屏。**UI 不要用 SLVideo overlay** |

## 四、图层结论

Steam Link 显示栈 = 视频层 + overlay 平面：
- SLVideo 硬解直接出视频层
- GUI 窗口（SDL + 原生 EGL，alpha=8）叠在视频层之上，**可行**
- 弹幕/UI 应画进 GUI 的 GL 层（nanovg），**不要**走 SLVideo overlay
- 编译必须 `-DEGL_API_FB`

## 五、播放器架构

- 视频源 / 音频源各一套：`StreamBuffer`（8MB 分块窗口）+ 自定义 AVIO + `AVFormatContext`
- 视频主线程：解封装 → `h264_mp4toannexb` → SLVideo
- 音频线程：自己解封装独立音频流（DASH）或消费主线程克隆的包（单文件）→ AAC 解码 → 44.1/48k 重采样 → SLAudio
- 音频预缓冲满时**等待**（不能丢帧），seek 通过请求/应答交给音频线程
- 自动音画同步：`GetQueuedVideoMS` 队列停止创新高 → 判定视频开始上屏 → 从音频预缓冲跳过“已呈现内容 P”后启动
- DASH：`playurl fnval=16`，视频取第一个 `avc1`，音频取最大 bandwidth；失败回退 `fnval=1` 单文件 MP4

## 六、当前移植方式

- 编译 wiliwili 整仓源码（UI/业务原样），**不改它的布局代码**
- 唯一替换点：`MPVCore`（头文件接口保留，实现换桩）→ 以后换成 SLVideo 播放器
- 依赖：cpr/pystring/borealis/lunasvg/OpenCC/QR/mongoose/libpdr；curl 用自编 7.79.1

## 七、VPU 鲁棒性架构（详见 [06-VPU鲁棒性架构.md](06-VPU鲁棒性架构.md)）

> 定位：**防止 VPU 卡死进入脏状态的播放器鲁棒性提升架构**。VPU 生命周期干净化是事前防御，进程隔离 + Dirty Flag 是事后兜底。

| 项 | 决策 | 理由 |
|---|---|---|
| 总体形态 | **进程隔离**：SlPlayer 跑独立子进程，wiliwili 主进程经 IPC 控制 | 子进程卡死可 SIGKILL + 重启，主进程/UI 不受影响；安全优先于少量 IPC 开销 |
| IPC 范围 | 只走控制面 + 事件面；视频帧/PCM 仍走 SLVideo/SLAudio 硬件层 | 双进程可同时访问硬件；数据不过 IPC，性能损失可忽略 |
| 脏退出检测 | **Dirty Flag**（`/tmp/slplayer_vpu.lock`），不做 1 帧 H.264 探针 | 探针自身创建/销毁 stream 可能成新污染源；失败无法区分码流错还是 VPU 脏 |
| watchdog 层级 | 放 **mpv 兼容层（主进程侧）独立线程**，不放 SlPlayer；只读无锁 `heartbeat()`，不 `_exit()` | 兼容层是语义转换点；监控者必须独立于被监控者，硬卡死时主循环会停摆，零线程版本失效 |
| SDK 复位能力 | 无全局 Deinit 可用，最接近复位的是 `FreeContext → 延时 → CreateContext` | `SLVideo.h` 只暴露 create/free，全仓头文件无 AMP/MV_OSAL 符号（已复核） |
| 落地顺序 | ① VPU 生命周期干净化 + Dirty Flag → ② `heartbeat()` + `setFatalCallback()` → ③ 进程隔离 + IPC + watchdog | 防御主体先行，每步独立可验证，不跳步 |
| 孤儿子进程清理 | 父进程意外退出时，`prctl(PR_SET_PDEATHSIG)` + `getppid()` 竞态检查 + IPC EOF 双保险；信号 handler 只置标志，主循环走 `shutdown()` | 避免 wiliwili 先死后播放子进程成孤儿占着 VPU；PDEATHSIG 是父**线程**语义且 handler 内不能调 VPU/锁，故需 EOF 兜底 + 复核 getppid（详见 06 的机制契约） |
| 落地纪律 | 按 [07 开发纪律](07-开发纪律.md) 执行；复核与回归记录写入 [02 日志](02-开发进度日志.md) | 避免基于想象设计；脏状态必须靠循环操作验证，不是"能播一次"就算过；播放/UI 结论必须采集卡截图确认 |
